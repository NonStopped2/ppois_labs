# Лабораторная работа №2 — «Почта»

> **Статус: реализованы все 50 предметных классов** — от оформления и оплаты
> до перевозки, курьерской доставки, розыска, компенсации и кассового учёта.
> Предметная библиотека и интерактивный CLI собираются из консоли и проверяются тестами.
> CI, документация генератором и релиз lab2 пока отсутствуют.

## 1. Описание проекта

Учебная объектная модель почтовой службы на **C++20**.
Сборка — **CMake**, unit-тесты — **Catch2**.

Источники требований:

- [Задание lab2](https://github.com/alix-zzh/ppois-course/blob/master/ru/lab2.md).
- [Общие требования](https://github.com/alix-zzh/ppois-course/blob/master/ru/common_requirements.md).
- [Чеклист](https://github.com/alix-zzh/ppois-course/blob/master/ru/checklist.md).

### Границы модели

Модель охватывает внутреннюю почту Беларуси: физические письма и посылки,
одну валюту BYN и шестизначные индексы. Международные перевозки, таможня,
наложенный платёж с переводом средств отправителю, реальные банковские
операции, сетевой сервер и графический интерфейс не входят в область модели.
Проверка структуры индекса не подтверждает существование адреса в реальном
справочнике.

Данные хранятся в памяти одного запуска. База данных и сохранение между
запусками не реализованы.

Основной процесс:

```text
Оформление → расчёт стоимости → оплата → приём в отделение → сортировка
→ перевозка → отделение назначения → выдача или курьерская доставка
```

Дополнительные процессы: повторная доставка, хранение, возврат, розыск и
компенсация. Это учебная модель, а не воспроизведение всех правил реального
почтового оператора или проверка подлинности документов.

### Сборка и тесты

Команды выполняются **из корня репозитория**. Нужны CMake ≥3.20 и компилятор
C++20. Для вспомогательных проверок нужен Python ≥3.9 без сторонних пакетов.
Catch2 v3.8.1 загружается автоматически с проверкой SHA-256; при первой
сборке тестов нужен доступ к сети.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target post_cli post_core_tests post_ui_tests --parallel 4
ctest --test-dir build -L '^lab2($|-)' --output-on-failure
./build/lab2/post_cli --demo
```

`post_cli` — приложение с интерактивным меню. Без `--demo` клиенты и отправления
изначально отсутствуют, с `--demo` добавляются примеры. Бинарник находится в
`<build-dir>/lab2/post_cli`. Справка: `./build/lab2/post_cli --help`.
Для сборки без тестов, Python и загрузки Catch2 используйте отдельный каталог
с `-DBUILD_TESTING=OFF` и цель `post_cli`. Внешний build-каталог поддерживается.
Подробная инструкция и примеры: **[CLI.md](CLI.md)**.

Покрытие требует Clang/AppleClang, совместимых `llvm-cov`, `llvm-profdata`
и Python ≥3.9 без сторонних Python-пакетов:

```bash
cmake -S . -B build/lab2-coverage -DCMAKE_BUILD_TYPE=Debug -DLAB2_ENABLE_COVERAGE=ON
cmake --build build/lab2-coverage --target post_core_tests post_ui_tests post_cli --parallel 4
python3 lab2/tools/coverage.py --build-dir build/lab2-coverage
python3 lab2/tools/coverage.py --build-dir build/lab2-coverage --with-ui
```

По умолчанию скрипт запускает только предметные C++ unit-тесты с точной меткой
`lab2` и считает `lab2/src/` и исполняемые строки `lab2/include/`.
Режим `--with-ui` добавляет C++ unit-тесты `lab2-ui` и производственный `app/`,
включая неисполняемый unit-тестами `main.cpp`. Для каждого запуска создаётся новый
каталог профилей; в обоих режимах проверяется **строго >90% строк**.
Внешние CLI-процессы и тесты Python не смешиваются с unit-профилями. Тесты,
Catch2, стандартная библиотека и lab1 не входят в область подсчёта.
Пути LLVM-инструментов задаются через `--llvm-cov` / `--llvm-profdata`;
на macOS по умолчанию используется `xcrun`.

Проверка с санитайзерами выполняется в отдельной сборке:

```bash
cmake -S . -B build/lab2-sanitized -DCMAKE_BUILD_TYPE=Debug -DLAB2_ENABLE_SANITIZERS=ON
cmake --build build/lab2-sanitized --target post_core_tests post_ui_tests post_cli --parallel 4
ctest --test-dir build/lab2-sanitized -L '^lab2($|-)' --output-on-failure
```

### Контракты реализованных классов

- **`Money`:** `explicit Money(int64_t kopecks = 0)`; `kopecks()` возвращает
  сумму, `add`, `subtract`, `multiply` возвращают новый `Money`. Доступны
  сравнения значений. Отрицательная сумма, отрицательный множитель,
  отрицательный результат и переполнение вызывают `InvalidAmountException`.
- **`Dimensions`:** конструктор принимает три положительные стороны `int64_t`,
  сохраняет их по убыванию. Поэтому `lengthMm()` — наибольшая сторона,
  `widthMm()` — средняя, `heightMm()` — наименьшая. `fitsWithin` допускает
  поворот и равенство пределу; `volumeCubicMm` и `lengthPlusGirthMm` проверяют
  арифметику. Ошибочные размеры дают `std::invalid_argument`, переполнение —
  `std::overflow_error`. Канонические тройки сравниваются по значению.
- **`PostalAddress`:** обязательны индекс, населённый пункт, улица и дом;
  `apartment` — `optional<string>`. Отсутствие квартиры допустимо, явно
  переданная пустая квартира ошибочна. Индекс состоит ровно из шести ASCII-цифр.
  ASCII-пробелы по краям удаляются, внутренние последовательности пробельных
  символов заменяются одним пробелом. Регистр не меняется, Unicode-нормализация
  и проверка кодировки UTF-8 не выполняются. `validate` вызывается конструктором;
  `sameDeliveryPointAs` сравнивает все нормализованные компоненты с учётом регистра.
  Доступны одноимённые геттеры полей. Ошибки дают `InvalidAddressException`.
- **`ContactDetails`:** телефон обязателен; храним `+` и от 7 до 15 ASCII-цифр,
  первая цифра не ноль. При вводе игнорируются ASCII-пробелы, дефисы и скобки;
  реальная страна, оператор и существование номера не проверяются. Email
  необязателен; переданная пустая строка ошибочна. Поддерживаем учебный формат
  `user@host.example`: один `@`, непустые части, домен с точкой, без пустых меток
  и дефисов по краям метки. Локальная часть содержит ASCII-буквы, цифры и
  `._%+-`, без точек по краям и повторных точек. Это не полный RFC-валидатор.
  `validate` проверяет контакты и предпочтение; `selectChannel` выбирает
  предпочтительный доступный канал либо первый поддерживаемый из переданного
  списка. Неизвестный канал и отсутствие подходящего дают `std::invalid_argument`.
  Геттеры: `phone`, `email`, `preferredChannel`.
- **`Customer`:** конструктор принимает идентификатор, имя, `PostalAddress`
  и `ContactDetails`. Идентификатор после нормализации не пуст и не содержит
  пробелов; имя не пусто. Управляющие ASCII-символы в текстовых полях запрещены,
  кроме пробельных, нормализуемых описанным выше способом. Геттеры `id`,
  `fullName`, `address`, `contacts` предоставляют только чтение. Адрес и контакты
  копируются по значению. Обновление исходных объектов не меняет клиента;
  копирование, присваивание и уничтожение обеспечиваются стандартными типами
  без собственных специальных функций — Rule of Zero.
- **`IdentityDocument`:** хранит `DocumentKind` (`Passport` или `IdentityCard`),
  номер, имя владельца и две календарные даты `std::chrono::year_month_day`.
  Номер и имя нормализуются как другие текстовые поля; номер не может содержать
  пробелы. Конструктор отклоняет неизвестный вид, пустые данные, невозможные
  даты и период с окончанием раньше выдачи через `std::invalid_argument`.
  `isValidOn(date)` включает обе граничные даты; невозможная дата запроса также
  даёт `std::invalid_argument`. `validateForHolder(name, date)` дополнительно
  сравнивает нормализованное имя с учётом регистра; чужой, просроченный или ещё
  не действующий документ даёт `DeliveryAuthorizationException`.
  Геттеры: `kind`, `number`, `holderName`, `issuedOn`, `expiresOn`.
  Формат государственного номера и подлинность документа не проверяются.
- **`ContentItem`:** имя, положительные `int64_t` количество и масса единицы
  в граммах, стоимость единицы `Money` и `ContentCategory`.
  Разрешены `Documents`, `GeneralGoods`, `FragileGoods`; `Prohibited`
  и неизвестные значения отклоняются. Неподходящие поля дают
  `InvalidShipmentDataException`. `totalWeightGrams` проверяет переполнение
  до умножения и даёт `std::overflow_error`; `totalDeclaredValue` использует
  проверенное умножение `Money` и даёт `InvalidAmountException` при переполнении.
  Нулевая стоимость допустима. Геттеры: `name`, `quantity`, `unitWeightGrams`,
  `unitDeclaredValue`, `category`. Классификация содержимого учебная и не
  заменяет полный перечень запретов реального почтового оператора.
- **`DeliveryOptions`:** по умолчанию все флаги выключены, объявленная ценность
  нулевая. Конструктор проверяет общие зависимости: регистрация и обязательная
  проверка документа включаются совместно; ненулевая ценность и уведомление
  требуют регистрации. `validateCombination(ShipmentKind)` допускает `Letter`
  или `Parcel`; хрупкость и курьерская доставка разрешены только посылке.
  Нарушения дают `IncompatibleServiceException`. `requiredServices` возвращает
  `vector<ServiceKind>` без повторов: регистрацию, объявленную ценность,
  курьерскую доставку, обработку хрупкого и уведомление согласно условиям.
  Проверка документа входит в регистрацию и отдельно не тарифицируется.
  Геттеры: `registered`, `declaredValue`, `identityCheckRequired`,
  `courierDelivery`, `fragile`, `notificationRequired`.
- **`TrackingEvent`:** положительный номер `int64_t`, известный
  `TrackingEventKind`, время `std::chrono::sys_seconds`, необязательный
  идентификатор отделения и описание. Поддерживаются метки начиная с эпохи Unix;
  отрицательное время отклоняется. Текст нормализуется, идентификатор не может
  содержать пробелы; явно переданное пустое отделение ошибочно. Отделение
  обязательно для всех видов, кроме `Information`, `Cancelled`, `Lost`.
  Объяснение обязательно для этих трёх видов и `DeliveryFailed`; в остальных
  случаях допустимо пустое описание. `validate` вызывается конструктором,
  ошибки дают `InvalidShipmentDataException`.
  Геттеры: `sequence`, `kind`, `occurredAt`, `branchId`, `description`.
- **`TrackingHistory`:** владеет `vector<TrackingEvent>`; `events()` предоставляет
  только чтение. `append` требует строго возрастающего номера (пропуски
  допустимы) и неубывающего времени. Ошибка даёт `InvalidShipmentStateException`
  до изменения истории. `eventsBetween(from, to)` возвращает независимую
  выборку с включёнными границами. `lastKnownBranch` возвращает последнее
  отделение события входа или выхода, у которого указан идентификатор.
  `timeSpentAt(branchId, asOf)` суммирует секунды пребывания до явно заданного
  момента, в том числе повторные посещения и незавершённый интервал.
  Будущие относительно `asOf` события не добавляют длительность.
  Входом считаются `Accepted`, `Arrived`, `AwaitingPickup`;
  выходом — `Dispatched`, `OutForDelivery`, `Delivered`, `Returned`, `Cancelled`, `Lost`.
  Терминальный `Returned` означает выдачу отправителю, а не начало нового хранения.
  Новый вход закрывает предыдущий интервал. Остальные виды, включая сообщения
  с указанным отделением, местоположение не меняют. Пустая история даёт пустую
  выборку, `nullopt` и нулевую длительность. Некорректный идентификатор запроса,
  отрицательное время или обратный интервал дают `std::invalid_argument`.
  Запросы и добавление не обращаются к системным часам. Обходы истории имеют
  линейную сложность, `append` — амортизированно константную по числу событий
  без учёта копирования текста. История проверяет хронологию, но не заменяет
  таблицу переходов состояния `Shipment`.
- **`Shipment`:** абстрактная база со снимками клиентов и собственной историей.
  `applyTrackingEvent` сначала проверяет переход, отделение и хронологию,
  готовит новую историю и лишь затем меняет статус. Приём требует регистрации
  и структурной готовности продукта; конкретные лимиты проверяются принимающим
  процессом через `validateForPosting`. Координацию с оплатой, полномочиями
  и складом выполняет `PostalBranch`. `revise(weight, options)` доступен
  только черновику и увеличивает `revision`, инвалидируя старый расчёт.
  `cancelBeforeAcceptance` записывает отмену с непустой причиной.
  `acceptedAt` фиксирует первый приём. `clone` сохраняет конкретный тип.
  Присваивание отправлений запрещено: оно не должно заменять идентификатор
  или часть базового состояния внутри реестра. Копирование снимка разрешено;
  даже передача rvalue в конструктор копии не опустошает исходное отправление.
- **`Letter`:** конверт, положительное число листов и нормализованное непустое
  описание. `validateForPosting(maxWeight, sizeLimit, maxUnits)` проверяет
  массу, габариты и число листов с включёнными верхними границами.
  Неположительные лимиты ошибочны; услуги должны подходить письму.
- **`Parcel`:** габариты, опись, упаковка `Box`/`PaddedEnvelope` и пломба.
  `addItem` работает только до пломбы; масса содержимого не превышает полную
  массу. Хрупкие предметы требуют коробки и услуги хрупкой обработки.
  `seal` требует непустую опись и идентификатор без пробелов.
  Проверка перед приёмом требует пломбу и дополнительно ограничивает общее
  количество единиц через `maxUnits`. Опись и версия не меняются при отказе.
  Изменение массы/опций через `revise` требует повторной проверки перед приёмом.
- **`ShipmentRegistry`:** владеет полиморфными копиями через `unique_ptr`.
  `registerShipment` принимает незарегистрированный черновик и явные лимиты,
  сохраняет оригинал и выдаёт уникальный внутри реестра номер `prefix-sequence`.
  После последнего представимого номера счётчик становится нулём, новые
  регистрации отклоняются без переполнения. `at` ищет в активных и архивных
  записях. Поиск клиента сравнивает идентификатор отправителя/получателя.
  `archiveCompletedBefore` использует строгую границу даты завершения,
  игнорирует поздние информационные сообщения и сохраняет адреса объектов.
  Ссылки действуют до уничтожения или замены реестра; его копии независимы.
- **`InvoiceLine`:** известный `ServiceKind`, непустое описание, положительное
  количество и цена `Money`. `BasePostage` обозначает основную пересылку,
  остальные виды — дополнительные услуги. `lineTotal` делегирует безопасное
  умножение `Money`; нулевая цена допустима. Некорректная строка вызывает
  `PaymentException`; переполнение — `InvalidAmountException`.

- **`TariffZone`:** положительный коэффициент в базисных пунктах (`10000 = 1`)
  и непустое покрытие префиксами из 1–6 ASCII-цифр. Повторяющиеся и вложенные
  префиксы внутри зоны запрещены. `covers` проверяет индекс адреса,
  `overlaps` — вложенность префиксов двух зон. Существование индекса не проверяется.
- **`WeightBand`:** интервал `(lowerExclusive, upperInclusive]`, положительный
  шаг, базовая цена первого начавшегося шага и цена каждого следующего.
  `priceFor(w) = basePrice + stepPrice × ((w − lower − 1) / step)` при целочисленном
  делении. Соседние интервалы не пересекаются; выход за интервал даёт
  `TariffNotFoundException`. Денежная арифметика проверяется `Money`.
- **`ServiceRate`:** дополнительная услуга и `RateMode::Fixed`/`Percentage`.
  В первом режиме процент нулевой, во втором фиксированная часть нулевая.
  `calculateSurcharge(basis, step)` принимает явную денежную базу, округляет
  процент вверх до копейки, затем до шага. Необязательный предел имеет приоритет
  над кратностью шагу: сумма никогда не превышает предел. Расчёт не использует
  `double` и не переполняет промежуточное произведение, если итог представим
  или ограничен пределом. `validateApplicability` требует подходящую выбранную
  опцию продукта. Основная пересылка не является дополнительной ставкой.
- **`TariffPlan`:** владеет зонами, весовыми интервалами и ставками; обе временные
  границы включены. `validateStructure` запрещает пересечения зон, одинаковые
  идентификаторы зон, пересечения весов и повторные услуги. Разрывы покрытия
  допустимы. `resolveRates(address, weight, time)` возвращает ссылки на единственную
  пару зоны/интервала; ссылки действуют до замены или уничтожения плана.
  Непокрытый адрес, вес, дата или отсутствующая ставка дают `TariffNotFoundException`.
- **`PostageQuote`:** неизменяемый снимок с трек-номером, версией отправления,
  идентификатором плана и включёнными временными границами. Строки должны
  содержать основную пересылку и не повторять виды услуг; итог проверяется
  на переполнение при создании. `validateFor(shipment, time)` требует черновик,
  совпадение трек-номера и версии, допустимую дату и точный набор выбранных услуг.
  Несоответствие даёт `PaymentException`. `total` суммирует принадлежащие снимку строки.

- **`PostageCalculator`:** владеет непустым набором планов с уникальными
  идентификаторами, положительным шагом округления и сроком предложения.
  `quote(shipment, planId, quoteId, time)` требует зарегистрированный структурно
  готовый черновик. База пересылки считается по весу, затем применяется зона.
  Для процента объявленной ценности база — объявленная ценность; для остальных
  процентных услуг — уже рассчитанная основная пересылка. Округляется каждая
  строка; отдельного скрытого округления итога нет. Срок обрезается окончанием
  плана без промежуточного переполнения даты. `compareAvailablePlans` возвращает
  доступные предложения по цене, затем по идентификатору плана; при отсутствии
  покрытия возвращает пустой список. Ошибки арифметики не скрываются.
- **`Payment`:** положительный `Money`, способ `Cash`/`Card`, идентификаторы
  оплаты/счёта и явная дата. `validateFor(invoice)` проверяет счёт, остаток,
  включённые временные границы, отсутствие дубля и общую хронологию денег.
  Это проверка финансовых условий, не обращение к банку и не проверка отправления.
- **`Refund`:** положительная сумма, непустая причина и ссылки по идентификаторам
  на оплату и счёт. `validateAgainst(payment, alreadyRefunded)` требует совпадение
  связей, дату не раньше оплаты и сумму в пределах ещё не возвращённой части.
  Возврат не является компенсацией за утрату.
- **`Invoice`:** независимый снимок предложения и два закрытых для записи журнала.
  Срок счёта целиком входит в срок предложения. `registerPayment(payment, shipment)`
  проверяет также актуальное отправление через `PostageQuote::validateFor`;
  изменённое отправление нельзя оплатить по старой цене. Переплата, дубли,
  операции задним числом и ошибки связей отклоняются до изменения журнала.
  `amountDue` вычитает возвраты из каждой исходной оплаты перед суммированием:
  даже оборот больше максимального `Money` не переполняет текущий баланс.
  Возврат заново открывает долг; допускается повторная оплата до истечения срока.
  Статусы: `Open`, `PartiallyPaid`, `Paid`, `PartiallyRefunded`, `Refunded`,
  `Cancelled`. `Refunded` не является отменой. После полного возврата можно
  вызвать `cancel`; с удержанными средствами отмена запрещена. У отменённого
  счёта нет долга и новые операции запрещены. Возврат возможен после истечения
  срока оплаты. Бесплатный счёт сразу `Paid`, без фиктивного нулевого платежа.
- **`StoragePolicy`:** бесплатные/максимальные дни, дневная цена, предел попыток
  и минимальные часы повтора. Настройки и интервалы проверяются на представимость.
  `deadlineFrom` прибавляет максимальный срок с проверкой переполнения даты.
  `chargeUntil` считает начавшиеся платные сутки и прекращает начисление на
  максимальном сроке; относительный расчёт не требует представимости будущей
  абсолютной даты. `canAttemptDelivery(storedAt, time, attemptsMade, lastAttempt)`
  требует согласованные количество и последнюю дату; ровно на дедлайне доставка
  уже запрещена, ровно на минимальном интервале повтор разрешён. Нулевой интервал
  повтора допустим. Отрицательные/обратные даты и несогласованная сводка ошибочны.

- **`StorageEntry`:** снимок номера, массы, размеров, места, времени поступления
  и дедлайна. Принимает только зарегистрированное отправление в состоянии
  нахождения в отделении и дату не раньше последнего события. `isOverdueAt`
  считает точную границу просроченной. `storageFeeUntil(policy, time)` применяет
  явно переданную политику и дополнительно ограничивает начисление сохранённым
  дедлайном; полная копия политики в записи не хранится. Запрос до поступления ошибочен.
- **`StorageCell`:** положительные лимиты общей массы и числа отправлений,
  габариты и принадлежащие ячейке записи. `place` проверяет все границы,
  отсутствие дубля и состояние отправления до вставки. `take` сначала готовит
  независимый результат, затем удаляет запись; неизвестный номер даёт
  `ShipmentNotFoundException`. Сумма масс не вычисляется с переполнением.
- **`StorageArea`:** уникальные изначально пустые ячейки и список продуктов.
  `General` хранит нехрупкие отправления, `Fragile` — хрупкие посылки.
  `planPlacement(shipments, policy, time)` выполняет first-fit на копиях ячеек
  и возвращает карту «трек-номер → ячейка» без изменения оригинала. Дубли,
  несовместимость и нехватка места дают `StorageCapacityException`.
  Оптимальная упаковка не гарантируется. `occupancyByKind(registry)` получает
  виды из авторитетного реестра. `place`/`take` предоставляют проверяемый доступ
  к принадлежащим зоне ячейкам; эти делегирующие операции отдельно не считаются.
- **`RouteStop`:** положительная позиция и неотрицательные интервалы в минутах,
  представимые в секундах; у позиции 1 предыдущая дорога нулевая.
  `earliestDeparture(arrival)` прибавляет только обработку с контролем даты.
- **`PostalRoute`:** не менее двух уникальных отделений с позициями 1…N,
  непустой набор `Van`/`Truck` без повторов и явный максимум длительности.
  `connects` проверяет направление, не разрешая обратный путь или ту же точку.
  `estimateDuration` суммирует движение и обработку, включая обработку первого
  и последнего пункта. Конфигурация и каждое сложение проверяются.

- **`Employee`:** роль, место работы и согласованные активность/причина
  отстранения. `authorize(operation, branchId)` требует активность и своё
  отделение. Всем ролям доступно начало своей смены; `Manager` — все известные
  операции, `Clerk` — приём/выдача/получение партии, `Sorter` — отправка/получение,
  `Courier` — доставка, `Driver` — управление транспортом, `Inspector` — осмотр и розыск.
  Отказ даёт `DeliveryAuthorizationException`; неизвестные значения ошибочны.
- **`WorkShift`:** расписание `[start, end)`, фактические даты и хронологические
  непересекающиеся перерывы. `start` проверяет сотрудника, отделение и время;
  `addBreak` допускает касание перерывов, но не их пересечение; `finish` не может
  предшествовать началу/перерывам и выходить за расписание. `workedDuration(asOf)`
  обрезает работу и перерывы моментом наблюдения, не начисляя сверх расписания.
  `overlaps` ищет пересечение расписаний одного сотрудника даже в разных отделениях.
  `isWorkingAt` требует именно активную смену и время вне перерыва; завершённая
  смена не разрешает провести новую операцию задним числом.
- **`SortingRule`:** непустые цифровые префиксы без вложений/повторов, известные
  продукты и неотрицательный приоритет. Большее число имеет преимущество.
  `matches` использует получателя при обычной отправке и отправителя при возврате.
  `conflictsWith` требует равный приоритет, пересечение покрытия/продуктов и разные
  направления. Одинаковое направление само по себе не создаёт неоднозначности.
- **`SortingPlan`:** непустой неизменяемый набор правил, положительная версия,
  запрет повторных ключей и направления в себя. `groupForDispatch` проверяет
  нахождение отправлений в своём отделении, отсутствие дублей и применимое правило,
  затем возвращает группы трек-номеров без изменения отправлений. Приоритет важнее
  длины префикса. Непокрытые отправления и неверное состояние отклоняются целиком.
- **`PickupAuthorization`:** конкретные отправление, доверитель, представитель
  и включённый срок. При возврате доверителем является исходный отправитель.
  `validateFor` требует состояние выдачи, актуальную дату, совпадение всех связей
  и документ представителя с верным именем/сроком. `revoke` необратим; повторный
  отзыв и попытка применить отозванное разрешение со старой датой запрещены.
  Календарное преобразование проверяет диапазон `std::chrono::year`, не позволяя
  огромному Unix-времени превратиться в другой год из-за усечения.

- **`MailBag`:** положительная вместимость, назначение и карта
  «трек-номер → сохранённая масса». `add` проверяет направление через
  `SortingPlan`, отсутствие дубля и общую массу без переполнения; назначение
  может быть промежуточным узлом, а не конечным адресным отделением.
  `remove` вычитает сохранённую массу. `seal` сверяет состав с реестром и датой,
  требует непустой мешок и фиксирует пломбу; после этого состав неизменяем.
  Включение в мешок само по себе не изымает груз из складской ячейки.
- **`DispatchBatch`:** разные источник/назначение, принадлежащие партии снимки
  запечатанных мешков и протокол `Draft → Ready → InTransit → Received`.
  `addBag` запрещает повтор мешка и любого отправления между мешками.
  `prepareForDispatch(route)` проверяет комплектацию и направление маршрута;
  это не датированный факт физического выбытия. Отправку фиксирует только
  `PostalBranch::transferOut`. `markReceived` требует факты прибытия всех номеров
  в реестре; согласованный приём со складом выполняется через `receiveBatch`.
  Масса и дата пломбы сверяются при движении. Неподходящий маршрут даёт
  `TransportUnavailableException`. Допуск и фактический ход проверяет `TransportTrip`.
- **`PostalBranch`:** владеет складом, карточками сотрудников и сменами, но не
  отправлениями. Конфигурация требует уникальные пустые зоны, согласованные
  назначения сотрудников/смен и покрытие собственного адреса. `authorize`
  проверяет собственную карточку, роль, активную смену и отсутствие перерыва.
  `acceptShipment` требует оплаченный непросроченный счёт, актуальный расчёт,
  явные лимиты и обслуживание адреса отправителя; затем принимает и размещает груз.
  `transferOut` сверяет весь состав партии и направления, записывает подготовку/
  выбытие и освобождает ячейки. `receiveBatch` проверяет суммарное размещение;
  конечное адресное отделение добавляет `AwaitingPickup`, промежуточное — нет.
  `issueShipment` проверяет размещение, покрытие, документ клиента либо разрешение
  представителю; при возврате выдаёт отправителю в исходном отделении.
  Смены изменяются через проверенные обёртки, не через изменяемые геттеры.
  Реестр, склад и партия подготавливаются на копиях и фиксируются без бросающих
  шагов между заменами. Успех инвалидирует старые ссылки на отправления и
  элементы склада: их нужно получить заново по номеру. Цена такой учебной схемы —
  копирование всего снимка реестра/склада, а не оптимизированная транзакция.
- **`ReturnRequest`:** черновик без мнимых дат, подача, одобрение/отказ и начало
  возврата — разные стадии. Клиент подаёт просьбу отправителя либо отказ получателя;
  уполномоченный сотрудник — основание истечения хранения. `approve` проверяет
  состояние, место, полномочия, хронологию, а для просрочки — сохранённый дедлайн
  и явно переданную политику. `reject` требует пояснение. `beginReturn` доступен
  после одобрения, повторно проверяет текущий контекст и при просрочке новый срок
  размещения; не переставляет снимки клиентов и не извлекает груз до отправки.
  Отказ при запуске сохраняет запрос, склад и историю без частичных изменений.
- **`DeliveryAttempt`:** неизменяемые дата, результат, причина и пояснение.
  Успех допускается только без причины отказа; неудача — с известной причиной
  и непустым пояснением. `canRetryAfter` разрешает только `RecipientAbsent` или
  `AddressNotFound`, начиная с точной границы минимального интервала.
  Отказ получателя и повреждение неповторяемы. Запросы не требуют сложения
  предельной даты с интервалом. Лимит числа попыток остаётся правилом `StoragePolicy`.

- **`Vehicle`:** положительные лимиты массы/мешков, известный вид и одно назначение.
  `assignTo` проверяет плановый рейс, его состав, маршрут и `VehicleInspection`;
  `releaseFrom` требует тот же завершённый рейс с выгруженными партиями.
  Предварительное резервирование допускается; выезд повторно проверяет допуск.
- **`VehicleInspection`:** включённый срок, машина, автор одобрения и карта дефектов.
  `addDefect` снимает допуск, `resolveDefect` не восстанавливает его автоматически.
  `approve` требует активного инспектора/руководителя и устранённых замечаний.
  `validateFor` проверяет конкретную машину, срок и текущее одобрение.
- **`TransportTrip`:** владеет рабочими снимками партий; `loadBatch` не изымает
  груз со склада. Все партии начинаются в первой точке; мешки, пломбы и номера
  уникальны в рейсе. `depart` сверяет ведомость, транспорт, допуск и обработку
  исходного пункта, затем согласованно изменяет рейс, машину, отделение и реестр.
  `arriveAt` допускает только следующую остановку после минимального времени дороги;
  нельзя проехать мимо невыгруженной партии. `unloadFor` проверяет обработку,
  полномочия и суммарную вместимость для всех партий пункта на общих копиях.
  Отдельный `lastActivityAt` не позволяет следующему прибытию предшествовать
  поздней выгрузке. `actualArrival` — последнее физическое прибытие, в том числе
  конечное. Финиш требует выгрузки; освобождение машины — отдельная операция.
  `maxDuration` ограничивает план маршрута, а не запрещает фактические опоздания.
- **`TransportManifest`:** независимые списки партий, пломбы и исходная общая масса.
  `buildFor` запрещает пустую ведомость и дату до создания груза/пломб;
  `verifyAgainst` сверяет рейс, порядок, пломбы и массу. Законная выгрузка меняет
  статус партии, но не исходный состав ведомости.
- **`SearchRequest`:** фиксирует отправление, заявителя, ожидаемый путь и номер
  последнего события `openedSequence`. Любое новое событие делает снимок устаревшим,
  даже при той же дате. Проверки подписывает работающий сотрудник с правом розыска;
  результат — дата, физическое наличие и пояснение. Отрицательный физический
  результат может расходиться с учётной записью ячейки. `resolveFound` требует
  положительный результат и согласованное размещение. `closeAsLost` требует все
  отрицательные проверки, явный минимальный срок и актуальную историю; затем
  отделение атомарно записывает `Lost` и удаляет оставшуюся учётную запись склада.

- **`Courier`:** активная карточка роли Courier, положительный лимит нагрузки и
  одно резервируемое назначение. `assignTask` проверяет общую массу без переполнения.
  `startRoute` повторно сверяет нагрузку, актуальные задания, работающего сотрудника
  своего отделения и согласованно выдаёт весь груз со склада с `OutForDelivery`.
  `finishRoute` требует обработанные задания; неудачные посылки физически возвращаются
  через `Arrived → AwaitingPickup` и размещаются все вместе либо не размещается ни одна.
- **`DeliveryRoute`:** владеет рабочими заданиями; повтор ключа и номера запрещён.
  `reorder` принимает только полную перестановку до начала. Попытки выполняются
  по очереди через проверяемые обёртки, без изменяемого геттера заданий.
  `nextPendingTask` возвращает заимствованный указатель только для чтения; после
  изменения/замены маршрута его надо получать заново. `complete` запрещает финиш,
  пока есть необработанный груз или неоформленный возврат после неудачи.
- **`DeliveryTask`:** фиксирует получателя, адрес, массу, исходные даты хранения,
  включённое окно и журнал попыток. Всё окно строго раньше исходного дедлайна.
  Физическая попытка требует текущей смены канонического сотрудника отделения,
  актуального назначения, окна и политики. Успех дополнительно требует документа
  получателя или разрешения представителю, применимого также в `OutForDelivery`.
  Запись попытки и история реестра фиксируются вместе. Новое задание и старый снимок
  не могут обнулить неудачи: журнал сверяется с фактами `DeliveryFailed` отправления.
  `reschedule` возможен лишь после складского возврата, при повторяемой причине,
  допустимом интервале и оставшемся лимите. Срок задания не продлевается новым размещением.
- **`CompensationClaim`:** заявитель — отправитель/получатель принятого отправления;
  сумма положительна, ссылки на доказательства непустые и уникальны. Утрата требует
  соответствующего завершённого розыска до подачи требования. Оценка ограничена
  запрошенной суммой, явным лимитом и ненулевой объявленной ценностью.
  Одобрение/мотивированный отказ требуют живых полномочий руководителя через отделение.
  Отдельный `decidedAt` запрещает выплату раньше решения; `markPaid` подтверждает
  точную одобренную сумму один раз. Учебные ссылки не доказывают подлинность ущерба;
  внешний лимит и оценку доказательств определяет уполномоченный сотрудник.
- **`CashRegister`:** сеанс своего отделения с наличным остатком и отдельными
  журналами платежей, возвратов и компенсаций. Кассовые операции требуют текущей
  смены кассира/руководителя. Карта не увеличивает наличность; возврат использует
  метод исходной оплаты. Оплата и возврат изменяют счёт/кассу на общих копиях;
  компенсация аналогично изменяет требование/кассу, но не счёт за пересылку.
  Не хватает наличности, повторён идентификатор, неверна дата или версия отправления —
  оба объекта остаются прежними. Закрытие требует сверки. Новый сеанс сбрасывает
  собственные журналы, но не может открыться раньше сохранённого `closedAt`.
  Однократность выплаты относится к каноническому объекту требования и ключам текущего
  журнала; глобального постоянного реестра требований и межкассового сервера нет.

Заголовки `detail/` содержат свободные функции, не дополнительные классы.
Перечисления, включая `ShipmentStatus` и `PackagingKind`, не включаются в счётчик
классов. Публичных сеттеров для обхода проверок нет; историю отправления нельзя
изменить отдельно от его статуса.

## 2. Общие правила модели

1. Деньги — целое число копеек BYN, без `double`. `Money` представляет
   неотрицательную сумму; отрицательный результат и переполнение запрещены.
   Знаковая разница кассы не представляется типом `Money`.
2. Вес — целое число граммов; размеры — целое число миллиметров. Арифметика
   проверяется на переполнение. Лимиты и тарифы задаются явно, не прячутся
   в магических числах внутри методов.
3. Идентификаторы не заменяют типизированные связи. Поле `shipmentId` само по
   себе не считается ассоциацией с `Shipment`.
4. Изменения статуса выполняются через доменные операции с проверкой перехода,
   а не публичным сеттером. CLI не получает возможность произвольно переписать
   статус.
5. При отклонении операции из-за бизнес-ошибки должно сохраняться исходное
   состояние всех затронутых объектов. Гарантии при ошибках выделения памяти
   зависят от контракта операции.
6. Время передаётся явно в операции, зависящие от дат. Проверки дат не требуют
   ожидания реального времени и не зависят от системных часов.
   Временные метки упорядочены.
7. В отправлении хранятся снимки данных отправителя, получателя и адреса.
   Последующее редактирование карточки клиента не меняет уже принятое отправление.
8. `ShipmentRegistry` — единственный владелец изменяемых
   отправлений. Остальные подсистемы хранят их идентификаторы и получают
   объекты через проверяемые операции.
9. История отслеживания принадлежит отправлению; отдельный реестр истории не
   предусмотрен. Задания доставки принадлежат маршруту доставки; у курьера
   хранятся их идентификаторы, а не независимые изменяемые копии.
10. `Letter` и `Parcel` специализируют `Shipment`.
    Унаследованные поля и общие поведения не учитываются повторно.
11. Оплата, возврат оплаты и компенсация — разные операции. Возврат ограничен
    суммой исходной оплаты; компенсация имеет собственное решение и лимит.
12. Перечисления статусов, ролей и видов услуг не учитываются как классы.
    Конструкторы, геттеры, сеттеры и технические вспомогательные методы не
    включаются в количественный счётчик содержательных поведений.

### Состояния отправления

Предусмотрены состояния: черновик, принято, подготовлено к отправке,
в пути, прибыло, передано курьеру, ожидает получения, вручено,
возвращается, возвращено, отменено, утрачено.

Переходы определяются доменными операциями; произвольная смена состояния
не допускается. Автомат состояний реализован и проверен для всех 12 × 13 пар
состояния и вида события с подходящим контекстом отделения и фазы возврата.
Основной путь: `Draft → Accepted → PreparedForDispatch → InTransit → Arrived`,
затем `AwaitingPickup` либо `OutForDelivery`, затем `Delivered`.
Для местного получателя приём сразу дополняется `Accepted → AwaitingPickup` без
искусственной перевозки. Из `Arrived` возможна следующая перевозка. `DeliveryFailed` сохраняет
`OutForDelivery`: физическое возвращение оформляется отдельным `Arrived`.
Возврат начинается из `Accepted`, `PreparedForDispatch`, `Arrived` или
`AwaitingPickup`; в `Returning` отдельно проверяется порядок подготовки,
отправки и прибытия по последнему неинформационному факту. `Returned` требует
исходного отделения. `Lost` допустим для принятого незавершённого отправления,
отмена — только для черновика. `Information` не меняет статус, в том числе
терминальный. Проверки оплаты, полномочий и склада остаются внешними процессами.
Получение оплаты само по себе не означает приём в отделение. Неудачная попытка
доставки не означает вручение. Терминальные состояния нельзя отменять обычным
переходом назад.

## 3. Правила подсчёта

- Каталог и реализация содержат **50 предметных классов**. Исключения учитываются
  отдельно от них.
- Учитываются собственные именованные поля предметных классов. Унаследованные
  поля повторно не считаются; внутренние поля стандартных контейнеров
  в подсчёт не входят. Параметры конструкторов производных классов, лишь
  передаваемые базовому классу, повторно не учитываются как ассоциации.
- Проектные поведения — **кандидаты содержательных операций**. Одинаковые
  правила, делегирующие обёртки и повторения при наследовании не считаются
  самостоятельными поведениями. Количество кандидатов не подтверждает
  количество реализованных уникальных операций. Технические UI-классы `Console`
  и `Application` из `app/` не увеличивают предметные количественные показатели.
- Связь — использование другого предметного класса как поля или типизированного
  параметра метода. Пара «класс → связанный класс» учитывается один раз.
  Наследование, строковые идентификаторы, только возвращаемые типы и стандартные
  типы в этот счётчик не включаются.
- Все 50 классов имеют постоянные unit-тесты в подкаталогах `tests/` по модулям.
- [Отдельный содержательный аудит](BEHAVIORS.md) исключает 23 спорных/повторяющихся
  кандидата из 133 операций каталога: остаётся **110 консервативно учитываемых
  поведений**. Обёртки маршрута, служебные проверки и методы управления сменами
  отделения дополнительно счётчик не увеличивают.

### A. Базовые данные — 6 классов

#### 01. `Money` — денежная сумма

- **Поля (1):** `kopecks` — неотрицательная сумма в копейках.
- **Поведения (3):** `add` — сложить суммы с проверкой переполнения;
  `subtract` — вычесть без отрицательного результата;
  `multiply` — умножить на неотрицательное целое количество с проверкой границы.
- **Связи:** нет межклассовых связей; параметры собственного типа не считаем.
- **Проверки:** ноль, обычные расчёты, предельная сумма, переполнение,
  отрицательный аргумент и неизменность исходных сумм при ошибке.

#### 02. `Dimensions` — габариты

- **Поля (3):** `lengthMm`, `widthMm`, `heightMm` — положительные размеры.
- **Поведения (3):** `fitsWithin` — проверить вхождение с перестановкой сторон;
  `volumeCubicMm` — вычислить объём без переполнения;
  `lengthPlusGirthMm` — вычислить наибольшую сторону плюс обхват остальных.
- **Связи:** нет межклассовых связей.
- **Проверки:** перестановки сторон, точное совпадение с лимитом,
  нулевые и отрицательные размеры, превышение и переполнение вычислений.

#### 03. `PostalAddress` — адрес доставки

- **Поля (5):** `postalCode`, `locality`, `street`, `building`, `apartment`;
  квартира необязательна, остальные поля обязательны.
- **Поведения (2):** `validate` — проверить структуру индекса и обязательные части;
  `sameDeliveryPointAs` — сравнить адреса по согласованным правилам нормализации,
  не учитывая имя получателя.
- **Связи:** нет межклассовых связей.
- **Проверки:** индекс с ведущим нулём, недопустимые символы, пустые части,
  отсутствие квартиры, различающиеся дома и квартиры.

#### 04. `ContactDetails` — способы связи

- **Поля (3):** `phone`, `email`, `preferredChannel`; электронная почта необязательна.
- **Поведения (2):** `validate` — проверить доступность обязательного контакта
  и поддерживаемый формат; `selectChannel` — выбрать допустимый способ
  уведомления с учётом предпочтения и доступных каналов.
- **Связи:** нет межклассовых связей.
- **Проверки:** допустимые разделители телефона, пустые контакты,
  некорректные данные, недоступный предпочтительный канал и резервный выбор.

#### 05. `IdentityDocument` — предъявленный документ

- **Поля (5):** `kind`, `number`, `holderName`, `issuedOn`, `expiresOn`.
- **Поведения (2):** `isValidOn` — проверить период действия на указанную дату;
  `validateForHolder` — проверить владельца, поддерживаемый вид документа
  и его действительность для предъявления.
- **Связи:** нет межклассовых связей.
- **Проверки:** граничные даты, выдача в будущем, истёкший срок,
  несовпадение владельца. Проверка подлинности реального документа не заявляется.

#### 06. `Customer` — отправитель или получатель

- **Поля (4):** `id`, `fullName`, `address` типа `PostalAddress`,
  `contacts` типа `ContactDetails`.
- **Поведения (0):** карточка хранит проверенные данные. Конструирование,
  чтение и простое обновление контактов не учитываются как уникальные поведения.
- **Связи:** `PostalAddress`, `ContactDetails`.
- **Проверки:** обязательные данные и независимость копий адреса и контактов.
  Снимки клиента внутри отправлений принадлежат этим отправлениям по значению.

### B. Отправления и отслеживание — 7 классов

#### 07. `Shipment` — общая модель отправления

- **Поля (9):** `trackingNumber`, `sender`, `recipient`, `weightGrams`,
  `options`, `status`, `history`, `acceptedAt`, `revision`. Клиенты — снимки
  `Customer`; опции — `DeliveryOptions`; история — `TrackingHistory`.
  `revision` меняется при изменении данных, влияющих на стоимость.
- **Поведения (3):** `applyTrackingEvent` — проверить переход состояния и
  согласованно дополнить историю; `cancelBeforeAcceptance` — отменить черновик;
  `revise` — изменить массу/опции черновика с инвалидированием расчёта.
  Общие абстрактные операции и технический `clone` не считаем.
- **Связи:** `Customer`, `DeliveryOptions`, `TrackingHistory`, `TrackingEvent`, `Dimensions`.
- **Проверки:** таблица переходов, повторная отмена, терминальные состояния,
  недопустимое событие и отсутствие частичного обновления истории.

#### 08. `Letter` — письмо

- **Поля (3):** `envelope` типа `Dimensions`, `sheetCount`, `contentsDescription`.
  Поля базового `Shipment` повторно не считаются.
- **Поведения (1):** `validateForPosting` — проверить ограничения именно письма:
  конверт, вес, количество листов и допустимые услуги.
- **Связи:** `Dimensions`. Наследование от `Shipment` отдельно не считаем.
- **Проверки:** допустимый конверт, границы веса и толщины,
  неподходящие услуги, сохранение свойств базового отправления.

#### 09. `Parcel` — посылка

- **Поля (4):** `dimensions` типа `Dimensions`, `contents` из `ContentItem`,
  `packagingKind`, `sealId`.
- **Поведения (3):** `addItem` — добавить допустимое содержимое до запечатывания;
  `seal` — запечатать подготовленную посылку;
  `validateForPosting` — проверить упаковку, содержимое, габариты, массу и услуги.
- **Связи:** `Dimensions`, `ContentItem`.
- **Проверки:** пустое содержимое, запрет изменения запечатанной посылки,
  масса содержимого больше полной массы, недопустимая упаковка и превышение лимита.

#### 10. `ContentItem` — позиция содержимого

- **Поля (5):** `name`, `quantity`, `unitWeightGrams`,
  `unitDeclaredValue` типа `Money`, `category`.
- **Поведения (2):** `totalWeightGrams` — вычислить полную массу позиции;
  `totalDeclaredValue` — вычислить полную объявленную стоимость позиции.
- **Связи:** `Money`.
- **Проверки:** количество и масса должны быть положительными;
  умножение проверяется на переполнение, неизвестная и запрещённая категории
  отклоняются. Совместимость содержимого и упаковки проверяет `Parcel`.

#### 11. `DeliveryOptions` — дополнительные условия

- **Поля (6):** `registered`, `declaredValue`, `identityCheckRequired`,
  `courierDelivery`, `fragile`, `notificationRequired`; объявленная ценность — `Money`.
- **Поведения (2):** `validateCombination` — проверить совместимость условий
  и вида отправления; `requiredServices` — получить набор реально необходимых
  платных услуг без повторного начисления одной услуги.
- **Связи:** `Money`.
- **Проверки:** объявленная ценность, хрупкость и обязательная проверка документа;
  разрешённые и запрещённые сочетания, отсутствие дублирующихся услуг.

#### 12. `TrackingEvent` — событие отслеживания

- **Поля (5):** `sequence`, `kind`, `occurredAt`, `branchId`, `description`.
- **Поведения (1):** `validate` — проверить состав события: для перемещения
  требуется отделение, для неудачной доставки — объяснение, номер положителен.
- **Связи:** нет; `branchId` сам по себе не считается ассоциацией.
- **Проверки:** обязательные данные для разных видов событий,
  недопустимый номер и корректная временная метка.

#### 13. `TrackingHistory` — упорядоченная история

- **Поля (1):** `events` — последовательность `TrackingEvent`.
- **Поведения (4):** `append` — добавить событие без нарушения порядка и повторов;
  `eventsBetween` — выбрать события за интервал;
  `lastKnownBranch` — найти последнее событие, задающее местоположение;
  `timeSpentAt` — вычислить длительность нахождения в отделении на заданный момент.
- **Связи:** `TrackingEvent`.
- **Проверки:** пустая история, одинаковые и убывающие номера,
  убывающие даты, информационные события без смены места и незавершённый интервал.

### C. Тарифы — 6 классов

#### 14. `TariffZone` — зона тарификации

- **Поля (4):** `id`, `name`, `postalPrefixes`, `priceFactorBasisPoints`.
- **Поведения (3):** `validateCoverage` — проверить префиксы и коэффициент;
  `covers` — определить принадлежность `PostalAddress` зоне;
  `overlaps` — обнаружить пересечение с другой зоной по префиксам.
- **Связи:** `PostalAddress`.
- **Проверки:** пустые и вложенные префиксы, ведущие нули,
  пересечение зон, адрес за пределами покрытия и границы коэффициента.

#### 15. `WeightBand` — весовой интервал тарифа

- **Поля (5):** `lowerExclusiveGrams`, `upperInclusiveGrams`,
  `basePrice`, `stepGrams`, `stepPrice`; цены — `Money`.
- **Поведения (3):** `contains` — проверить принадлежность интервалу;
  `priceFor` — рассчитать цену с округлением оплачиваемых весовых шагов вверх;
  `overlaps` — обнаружить пересечение двух весовых интервалов.
- **Связи:** `Money`.
- **Проверки:** обе границы интервала, полный и неполный шаг,
  нулевой шаг, разрыв и пересечение интервалов, переполнение цены.

#### 16. `ServiceRate` — ставка дополнительной услуги

- **Поля (5):** `service`, `mode`, `fixedCharge`, `basisPoints`,
  `maximumCharge`; денежные значения — `Money`, предел может отсутствовать.
- **Поведения (2):** `calculateSurcharge` — рассчитать фиксированный или
  процентный сбор с заданным округлением и пределом;
  `validateApplicability` — проверить доступность услуги для выбранного продукта.
- **Связи:** `Money`, `DeliveryOptions`.
- **Проверки:** фиксированная и процентная ставка, денежное округление,
  верхний предел, неизвестная или недоступная услуга.

#### 17. `TariffPlan` — согласованный набор тарифов

- **Поля (7):** `id`, `name`, `validFrom`, `validUntil`,
  `zones` из `TariffZone`, `weightBands` из `WeightBand`,
  `serviceRates` из `ServiceRate`.
- **Поведения (2):** `validateStructure` — обнаружить конфликтующие зоны,
  интервалы и повторяющиеся услуги; `resolveRates` — подобрать однозначные
  зону и ставки для адреса, веса и даты либо отклонить расчёт.
- **Связи:** `TariffZone`, `WeightBand`, `ServiceRate`, `PostalAddress`.
- **Проверки:** срок действия, пропущенный диапазон веса,
  неоднозначное покрытие и отсутствие нужной услуги.

#### 18. `PostageCalculator` — расчёт стоимости

- **Поля (3):** `tariffPlans` из `TariffPlan`,
  `roundingStepKopecks`, `quoteLifetime`.
- **Поведения (2):** `quote` — рассчитать `PostageQuote` для `Shipment` с
  применением зоны, массы и услуг; `compareAvailablePlans` — сравнить доступные
  предложения с сохранением информации о применённом плане.
- **Связи:** `TariffPlan`, `Shipment`. Возвращаемый `PostageQuote` не считаем.
- **Проверки:** состав цены, несколько доступных планов,
  отсутствие подходящего плана, срок предложения и детерминированный результат.

#### 19. `PostageQuote` — предварительное ценовое предложение

- **Поля (7):** `id`, `shipmentTrackingNumber`, `shipmentRevision`,
  `tariffPlanId`, `createdAt`, `expiresAt`, `lines` из `InvoiceLine`.
- **Поведения (2):** `total` — вычислить итог по строкам без переполнения;
  `validateFor` — проверить соответствие `Shipment`, его версии и моменту оплаты.
- **Связи:** `InvoiceLine`, `Shipment`. Возвращаемый `Money` не считаем.
- **Проверки:** просроченное предложение, другая посылка,
  изменение веса или услуг после расчёта, независимость снимка строк.

### D. Оплата — 5 классов

#### 20. `InvoiceLine` — строка начисления

- **Поля (4):** `service`, `description`, `quantity`, `unitPrice` типа `Money`.
- **Поведения (1):** `lineTotal` — вычислить сумму начисления с проверкой
  количества и денежной арифметики.
- **Связи:** `Money`.
- **Проверки:** положительное количество, нулевая ставка,
  переполнение и соответствие описания виду услуги.

#### 21. `Invoice` — начисление к оплате

- **Поля (7):** `id`, `quote` типа `PostageQuote`, `issuedAt`,
  `expiresAt`, `status`, `payments` из `Payment`, `refunds` из `Refund`.
- **Поведения (4):** `amountDue` — рассчитать остаток к оплате;
  `registerPayment` — принять подходящую оплату без дублирования и переплаты;
  `registerRefund` — учесть возврат в пределах конкретной оплаты;
  `cancel` — отменить счёт без удержанных средств по допустимому переходу.
- **Связи:** `PostageQuote`, `Payment`, `Refund`, `Shipment`. Возвращаемый `Money` не считаем.
- **Проверки:** частичная и полная оплата, чужой счёт, дубликат,
  переплата, повторный возврат и отмена оплаченного счёта.

#### 22. `Payment` — факт оплаты

- **Поля (5):** `id`, `invoiceId`, `amount` типа `Money`, `method`, `paidAt`.
- **Поведения (1):** `validateFor` — проверить принадлежность `Invoice`,
  положительную сумму, оставшуюся задолженность и допустимое время оплаты.
- **Связи:** `Money`, `Invoice`.
- **Проверки:** нулевая сумма, истёкший счёт, несоответствие идентификатора
  и оплата сверх остатка. Реального обращения к банку нет.

#### 23. `Refund` — возврат оплаты

- **Поля (6):** `id`, `paymentId`, `invoiceId`, `amount` типа `Money`,
  `createdAt`, `reason`.
- **Поведения (1):** `validateAgainst` — проверить исходную `Payment`,
  причину, дату и сумму с учётом уже выполненных возвратов.
- **Связи:** `Money`, `Payment`.
- **Проверки:** полный и частичный возврат, превышение доступной суммы,
  чужая оплата, возврат до оплаты и отсутствие причины.

#### 24. `CashRegister` — касса отделения

- **Поля (10):** `id`, `branchId`, `openingBalance`, `cashBalance`,
  `payments` из `Payment`, `refunds` из `Refund`, `compensations`,
  `isOpen`, `openedAt`, `closedAt`. Остатки и суммы компенсаций — `Money`.
- **Поведения (6):** `open` — открыть кассу с начальным остатком;
  `acceptPayment` — согласованно провести оплату через `Invoice` с проверкой живого `Shipment`;
  `refundPayment` — провести связанный возврат при достаточном остатке;
  `payCompensation` — выплатить одобренную `CompensationClaim` один раз;
  `reconcile` — проверить фактическую наличность против учётной;
  `close` — завершить работу открытой кассы после сверки.
- **Связи:** `Money`, `Payment`, `Refund`, `Invoice`, `Shipment`, `CompensationClaim`, `PostalBranch`.
- **Проверки:** закрытая касса, повторное открытие, наличная и учётная
  безналичная оплата, нехватка наличности, повторная выплата и атомарность со счётом.

### E. Отделение и хранение — 6 классов

#### 25. `PostalBranch` — почтовое отделение

- **Поля (7):** `id`, `name`, `address` типа `PostalAddress`,
  `storageAreas` из `StorageArea`, `employees` из `Employee`,
  `workShifts` из `WorkShift`, `servedPostalPrefixes`.
- **Поведения (4):** `acceptShipment` — принять оплаченное `Shipment` по `Invoice`
  и разместить его; `transferOut` — передать хранимое отправление в `DispatchBatch`;
  `receiveBatch` — принять партию с предварительной проверкой размещения;
  `issueShipment` — вручить отправление надлежащему `Customer` после проверки
  `IdentityDocument` и при необходимости `PickupAuthorization`.
- **Связи:** `PostalAddress`, `StorageArea`, `Employee`, `WorkShift`, `Shipment`,
  `Invoice`, `DispatchBatch`, `Customer`, `IdentityDocument`,
  `PickupAuthorization`, `ShipmentRegistry`, `StoragePolicy`, `Dimensions`, `SortingPlan`.
- **Проверки:** неоплаченный приём, чужое отделение, нехватка места,
  повторный приём партии, выдача другому лицу и отсутствие частичного перемещения.

#### 26. `StorageArea` — зона хранения

- **Поля (5):** `id`, `name`, `kind`, `cells` из `StorageCell`,
  `allowedShipmentKinds`.
- **Поведения (2):** `planPlacement` — подобрать размещение набора `Shipment`
  по совместимости и свободным ячейкам без изменения состояния;
  `occupancyByKind` — вычислить загрузку по видам отправлений.
- **Связи:** `StorageCell`, `Shipment`, `StoragePolicy`, `ShipmentRegistry`.
- **Проверки:** неподходящий тип отправления, заполненная зона,
  несколько ячеек, отсутствие изменения при неудачном плане.
  План не обязан находить математически оптимальную упаковку.

#### 27. `StorageCell` — ячейка хранения

- **Поля (5):** `id`, `maxWeightGrams`, `maxItems`,
  `limit` типа `Dimensions`, `entries` из `StorageEntry`.
- **Поведения (2):** `place` — разместить `Shipment` с проверкой массы,
  габаритов, количества и отсутствия дубликата; `take` — извлечь имеющееся
  отправление, сохранив данные о размещении для вызывающей операции.
- **Связи:** `Dimensions`, `StorageEntry`, `Shipment`, `StoragePolicy`.
- **Проверки:** точные границы всех лимитов, повторное размещение,
  отсутствие отправления и неизменность занятого места после ошибки.

#### 28. `StorageEntry` — запись о размещении

- **Поля (6):** `shipmentId`, `storedWeightGrams`, `dimensions` типа `Dimensions`,
  `receivedAt`, `deadlineAt`, `cellId`.
- **Поведения (2):** `isOverdueAt` — определить просрочку на указанный момент;
  `storageFeeUntil` — рассчитать стоимость хранения по `StoragePolicy`.
- **Связи:** `Dimensions`, `StoragePolicy`, `Shipment`.
- **Проверки:** момент ровно на границе срока, бесплатные дни,
  неполные оплачиваемые сутки и запрос времени до поступления.

#### 29. `Employee` — сотрудник

- **Поля (6):** `id`, `fullName`, `role`, `branchId`, `active`, `suspensionReason`.
- **Поведения (1):** `authorize` — проверить операцию, роль, активность
  и идентификатор отделения. Сам объект отделения проверке не требуется.
- **Связи:** нет; строковый идентификатор отделения не считается ассоциацией.
- **Проверки:** допустимые и запрещённые операции для каждой роли,
  неактивный сотрудник и чужое отделение. Простые обновления карточки не считаем.

#### 30. `WorkShift` — рабочая смена

- **Поля (9):** `id`, `employeeId`, `branchId`, `scheduledStart`,
  `scheduledEnd`, `actualStart`, `actualEnd`, `breaks`, `state`.
- **Поведения (6):** `start` — начать назначенную смену `Employee` в отделении с заданным идентификатором;
  `addBreak` — учесть непересекающийся перерыв в допустимых границах;
  `finish` — завершить начатую смену;
  `workedDuration` — вычислить фактически отработанное время без перерывов;
  `overlaps` — выявить конфликт расписаний одного сотрудника;
  `isWorkingAt` — проверить текущую доступность с учётом состояния и перерывов.
- **Связи:** `Employee`; идентификатор отделения не считается ассоциацией.
- **Проверки:** конец раньше начала, повторное начало, перерыв за границами,
  пересекающиеся перерывы, соседние смены и незавершённая смена.

### F. Сортировка — 4 класса

#### 31. `SortingRule` — правило сортировки

- **Поля (5):** `id`, `destinationPrefixes`, `nextBranchId`,
  `priority`, `allowedShipmentKinds`.
- **Поведения (2):** `matches` — проверить применимость к `Shipment`;
  `conflictsWith` — обнаружить неоднозначность с другим правилом
  одинакового приоритета и пересекающегося покрытия.
- **Связи:** `Shipment`.
- **Проверки:** пересекающиеся префиксы, разные приоритеты,
  ограничения по виду и конфликт направлений.

#### 32. `SortingPlan` — план сортировки отделения

- **Поля (4):** `id`, `branchId`, `rules` из `SortingRule`, `version`.
- **Поведения (2):** `validateRules` — проверить конфликты и ошибочное
  направление обратно в то же отделение;
  `groupForDispatch` — распределить набор `Shipment` по направлениям,
  выбрав правило по приоритету и отклонив неразрешимую неоднозначность.
- **Связи:** `SortingRule`, `Shipment`.
- **Проверки:** отсутствие правила, конфликт, однозначный выбор
  по приоритету и группировка нескольких направлений.

#### 33. `MailBag` — почтовый мешок

- **Поля (7):** `id`, `maxWeightGrams`, `destinationBranchId`,
  `sealedAt`, `sealId`, `shipmentIds` (карта номеров и снимков массы), `totalWeightGrams`.
- **Поведения (3):** `add` — включить `Shipment` для соответствующего
  `PostalBranch` по `SortingPlan` без перегруза и дубля;
  `remove` — извлечь отправление до запечатывания;
  `seal` — запечатать непустой мешок и запретить изменение состава.
- **Связи:** `Shipment`, `PostalBranch`, `SortingPlan`, `ShipmentRegistry`.
- **Проверки:** точная предельная масса, другое направление,
  повторное включение, пустой мешок и изменение после запечатывания.

#### 34. `DispatchBatch` — партия к отправке

- **Поля (6):** `id`, `sourceBranchId`, `targetBranchId`,
  `bags` из `MailBag`, `status`, `createdAt`.
- **Поведения (3):** `addBag` — включить подходящий запечатанный мешок;
  `prepareForDispatch` — проверить полноту партии и соответствие `PostalRoute`;
  `markReceived` — подтвердить получение нужным `PostalBranch` без повторения.
- **Связи:** `MailBag`, `PostalRoute`, `PostalBranch`, `ShipmentRegistry`.
- **Проверки:** разные назначения мешков, незапечатанный мешок,
  неподходящий маршрут, приём не тем отделением и повторное получение.

### G. Междугородняя перевозка — 6 классов

#### 35. `PostalRoute` — маршрут между отделениями

- **Поля (5):** `id`, `name`, `stops` из `RouteStop`,
  `maxDuration`, `allowedVehicleTypes`.
- **Поведения (3):** `validateSequence` — проверить порядок остановок
  и параметры пути; `connects` — проверить достижимость назначения после
  отправления по порядку маршрута; `estimateDuration` — вычислить длительность
  с учётом перемещений и обработки на остановках.
- **Связи:** `RouteStop`.
- **Проверки:** недостаточное количество остановок, неверный порядок,
  направление пути, отрицательные интервалы и превышение допустимой длительности.

#### 36. `RouteStop` — остановка маршрута

- **Поля (4):** `branchId`, `sequence`, `travelMinutesFromPrevious`,
  `handlingMinutes`.
- **Поведения (1):** `earliestDeparture` — вычислить самое раннее отправление
  после прибытия с учётом обязательного времени обработки и границ времени.
- **Связи:** нет межклассовых связей.
- **Проверки:** нулевая обработка, отрицательный интервал,
  переполнение даты и корректная первая остановка.

#### 37. `Vehicle` — транспорт

- **Поля (7):** `id`, `registrationNumber`, `maxWeightGrams`, `maxBags`,
  `state`, `assignedTripId`, `type`.
- **Поведения (2):** `assignTo` — выделить транспорт под `TransportTrip`
  после проверки вместимости `DispatchBatch` и допуска `VehicleInspection`;
  `releaseFrom` — освободить транспорт только после допустимого завершения рейса.
- **Связи:** `TransportTrip`, `VehicleInspection`. Доступ к партиям через рейс
  не считается отдельным полем или параметром `DispatchBatch`.
- **Проверки:** перегруз, лимит мешков, занятость, неподходящий вид,
  просроченный осмотр и освобождение из чужого рейса.

#### 38. `VehicleInspection` — допуск транспорта

- **Поля (7):** `id`, `vehicleId`, `inspectedAt`, `expiresAt`,
  `inspectorId`, `defects`, `approved`; замечания имеют отметку об устранении.
- **Поведения (4):** `addDefect` — зарегистрировать замечание и снять допуск;
  `resolveDefect` — отметить устранение известного замечания;
  `approve` — выдать допуск уполномоченным `Employee` при устранённых замечаниях;
  `validateFor` — проверить соответствие `Vehicle`, срок и действующий допуск.
- **Связи:** `Employee`, `Vehicle`.
- **Проверки:** незакрытое замечание, неизвестный дефект, недостаточные права,
  другой транспорт и границы срока осмотра.

#### 39. `TransportTrip` — конкретный рейс

- **Поля (9):** `id`, `route` типа `PostalRoute`, `vehicleId`,
  `batches` из `DispatchBatch`, `state`, `actualDeparture`,
  `actualArrival`, `currentStopIndex`, `lastActivityAt`.
- **Поведения (4):** `loadBatch` — погрузить партию с учётом пути и вместимости;
  `depart` — начать рейс на подходящем `Vehicle` с `VehicleInspection`;
  `arriveAt` — зафиксировать следующую остановку `PostalBranch`;
  `unloadFor` — выгрузить партии только в их пункте назначения.
- **Связи:** `PostalRoute`, `DispatchBatch`, `Vehicle`, `VehicleInspection`,
  `PostalBranch`, `ShipmentRegistry`, `SortingPlan`, `TransportManifest`, `StoragePolicy`.
- **Проверки:** загрузка после старта, неверная остановка,
  выгрузка раньше назначения, повторный старт и хронология рейса.

#### 40. `TransportManifest` — транспортная ведомость

- **Поля (6):** `id`, `tripId`, `issuedAt`, `batchIds`,
  `seals`, `declaredWeightGrams`.
- **Поведения (2):** `buildFor` — составить снимок состава `TransportTrip`,
  пломб и массы; `verifyAgainst` — обнаружить изменение состава,
  пломб или массы по сравнению с ведомостью.
- **Связи:** `TransportTrip`.
- **Проверки:** совпадение снимка, недостающая и лишняя партия,
  подмена пломбы, другой рейс и независимость от последующих изменений.

### H. Доставка и получение — 6 классов

#### 41. `Courier` — курьер

- **Поля (5):** `employee` типа `Employee`, `vehicleId`, `maxLoadGrams`,
  `assignedTaskIds`, `activeRouteId`.
- **Поведения (3):** `assignTask` — назначить `DeliveryTask` без перегруза
  и повторного назначения; `startRoute` — начать согласованный `DeliveryRoute`
  действующим сотрудником; `finishRoute` — закрыть маршрут после обработки заданий.
- **Связи:** `Employee`, `DeliveryTask`, `DeliveryRoute`, `PostalBranch`, `ShipmentRegistry`, `StoragePolicy`.
- **Проверки:** роль и активность, превышение нагрузки, чужое задание,
  параллельный маршрут и незавершённые задания.

#### 42. `DeliveryRoute` — маршрут вручения

- **Поля (6):** `id`, `courierId`, `tasks` из `DeliveryTask`,
  `startedAt`, `finishedAt`, `currentTaskIndex`.
- **Поведения (4):** `addTask` — включить задание до начала маршрута;
  `reorder` — изменить порядок без потерь и дублей;
  `nextPendingTask` — выбрать очередное необработанное задание;
  `complete` — завершить маршрут только при обработанных заданиях.
- **Связи:** `DeliveryTask`, `Courier`, `ShipmentRegistry`, `PostalBranch`, `DeliveryAttempt`, `StoragePolicy`, `Customer`, `IdentityDocument`, `PickupAuthorization`.
- **Проверки:** повтор задания, неверная перестановка,
  изменение начатого маршрута, пропуск обработанных заданий и раннее завершение.

#### 43. `DeliveryTask` — задание на доставку

- **Поля (11):** `id`, `shipmentId`, `recipient` типа `Customer`,
  `address` типа `PostalAddress`, `weightGrams`, `scheduledWindow`,
  `attempts` из `DeliveryAttempt`, `state`, `courierId`, `storageReceivedAt`, `storageDeadlineAt`.
- **Поведения (4):** `schedule` — согласовать окно и назначение `Courier`;
  `recordAttempt` — добавить допустимую попытку без нарушения порядка;
  `completeDelivery` — вручить `Shipment` после проверки клиента,
  `IdentityDocument` и при необходимости `PickupAuthorization`;
  `reschedule` — назначить новое окно после допускающей повтор неудачи.
- **Связи:** `Customer`, `PostalAddress`, `DeliveryAttempt`, `Courier`,
  `Shipment`, `IdentityDocument`, `PickupAuthorization`, `StorageEntry`, `StoragePolicy`, `ShipmentRegistry`, `PostalBranch`.
- **Проверки:** неправильное окно, чужой курьер, повтор вручения,
  неверный получатель, порядок попыток и перенос уже завершённого задания.

#### 44. `DeliveryAttempt` — попытка вручения

- **Поля (5):** `id`, `attemptedAt`, `outcome`, `failureReason`, `note`.
- **Поведения (2):** `validateOutcome` — проверить согласованность результата
  и обязательной причины неудачи; `canRetryAfter` — проверить допустимость
  повтора по результату и минимальному интервалу между попытками.
- **Связи:** нет межклассовых связей.
- **Проверки:** успешная попытка с причиной отказа, неудача без причины,
  неповторяемый отказ и граница минимального интервала.

#### 45. `PickupAuthorization` — разрешение представителю

- **Поля (7):** `id`, `shipmentId`, `principalCustomerId`,
  `representativeCustomerId`, `validFrom`, `validUntil`, `revokedAt`.
- **Поведения (2):** `validateFor` — проверить `Shipment`, представляемого,
  представителя `Customer`, его `IdentityDocument` и срок;
  `revoke` — отозвать разрешение без возможности дальнейшего использования.
- **Связи:** `Shipment`, `Customer`, `IdentityDocument`.
- **Проверки:** чужое отправление, другой представитель,
  начало и конец срока, просрочка и повторное использование отозванного разрешения.

#### 46. `StoragePolicy` — правила хранения и повторной доставки

- **Поля (6):** `id`, `freeStorageDays`, `maxStorageDays`,
  `dailyFee` типа `Money`, `maxDeliveryAttempts`, `minRetryHours`.
- **Поведения (3):** `deadlineFrom` — вычислить предельный срок;
  `chargeUntil` — рассчитать платные дни с явно заданным округлением
  и ограничением начисления сроком хранения;
  `canAttemptDelivery` — проверить срок и лимит попыток.
- **Связи:** `Money`.
- **Проверки:** бесплатный период, начавшиеся платные сутки,
  истечение хранения, последняя разрешённая попытка и недопустимые настройки.

### I. Возврат, розыск и компенсация — 3 класса

#### 47. `ReturnRequest` — основание для возврата

- **Поля (9):** `id`, `shipmentId`, `initiatorId`, `initiatorKind`,
  `reason`, `requestedAt`, `status`, `decidedAt`, `decisionReason`.
- **Поведения (4):** `submit` — зарегистрировать допустимое обращение
  `Customer` или `Employee` по `Shipment`;
  `approve` — подтвердить основание с учётом состояния и `StoragePolicy`;
  `reject` — вынести мотивированный отказ;
  `beginReturn` — начать обратный путь из `PostalBranch`, сохранив исходные
  сведения об отправителе и получателе.
- **Связи:** `Shipment`, `Customer`, `Employee`, `StoragePolicy`, `PostalBranch`, `ShipmentRegistry`.
- **Проверки:** чужой заявитель, уже вручённое отправление,
  запрос во время перевозки, истечение хранения и повторное решение.

#### 48. `SearchRequest` — розыск отправления

- **Поля (11):** `id`, `shipmentId`, `applicantCustomerId`, `openedAt`,
  `lastKnownBranchId`, `expectedBranchIds`, `checkedBranchIds`,
  `findings`, `status`, `closedAt`, `openedSequence`.
- **Поведения (4):** `open` — открыть розыск `Shipment` по обращению
  надлежащего `Customer` и ожидаемому пути `PostalRoute`;
  `recordBranchCheck` — учесть результат проверки `PostalBranch` без дубля;
  `resolveFound` — закрыть розыск обнаруженного отправления;
  `closeAsLost` — признать утрату после выполнения обязательных проверок.
- **Связи:** `Shipment`, `Customer`, `PostalRoute`, `PostalBranch`, `ShipmentRegistry`.
- **Проверки:** посторонний заявитель, вручённое отправление,
  непроверенные отделения, повторная проверка и закрытый розыск.

#### 49. `CompensationClaim` — требование компенсации

- **Поля (12):** `id`, `shipmentId`, `claimantCustomerId`, `claimedAmount`,
  `approvedAmount`, `reason`, `submittedAt`, `status`, `evidenceReferences`,
  `decisionReason`, `paidAt`, `decidedAt`; суммы — `Money`.
- **Поведения (5):** `submit` — принять требование надлежащего `Customer`
  по `Shipment`; `assess` — определить допустимый предел с учётом основания,
  объявленной ценности и при утрате `SearchRequest`;
  `approve` — зафиксировать решение через канонические полномочия `PostalBranch` в пределах оценки;
  `reject` — мотивированно отклонить требование;
  `markPaid` — подтвердить выплату только одобренной суммы один раз.
- **Связи:** `Money`, `Shipment`, `Customer`, `SearchRequest`, `PostalBranch`.
- **Проверки:** необоснованное обращение, чужой заявитель,
  превышение предела, выплата до одобрения и повторная выплата.

### J. Реестр — 1 класс

#### 50. `ShipmentRegistry` — учёт отправлений

- **Поля (4):** `shipments`, `archivedShipments`, `nextSequence`, `trackingPrefix`;
  активные и архивные коллекции владеют разными объектами `Shipment`.
- **Поведения (4):** `registerShipment` — выдать уникальный трек-номер
  и зарегистрировать корректное отправление;
  `findByStatus` — выбрать отправления по состоянию;
  `findByCustomer` — найти отправления с участием `Customer`;
  `archiveCompletedBefore` — переместить завершённые записи в архив,
  сохранив возможность отслеживания по номеру.
- **Связи:** `Shipment`, `Customer`, `Dimensions`.
- **Проверки:** уникальность номера, предел счётчика,
  неизвестное отправление, поиск активных и архивных записей,
  запрет архивации незавершённого отправления.

## 5. Исключения

Каждое исключение определяется в собственном заголовке под
`include/post/exceptions/`. Реализованы `PostalException` как наследник
`std::runtime_error` и тринадцать его наследников: `InvalidAmountException`,
`InvalidAddressException`, `InvalidShipmentDataException`,
`IncompatibleServiceException`, `InvalidShipmentStateException`,
`DeliveryAuthorizationException`, `ShipmentLimitExceededException`,
`ShipmentNotFoundException`, `PaymentException`, `TariffNotFoundException`,
`StorageCapacityException`, `TransportUnavailableException`, `ManifestMismatchException`.
Для обычных ошибок аргументов допустимы стандартные исключения, но они не
включаются в счётчик собственных типов.

| Класс | Когда возникает | Основные источники |
|---|---|---|
| `PostalException` | Общий базовый тип для обработки ошибок почтовой модели | База конкретных исключений |
| `InvalidAmountException` | Отрицательная сумма, недопустимое денежное действие или переполнение | `Money`, денежные расчёты |
| `InvalidAddressException` | Некорректный индекс или обязательная часть адреса | `PostalAddress` |
| `InvalidShipmentDataException` | Некорректные данные, содержимое, событие или упаковка отправления | `ContentItem`, `TrackingEvent`, `Shipment`, `Letter`, `Parcel` |
| `ShipmentLimitExceededException` | Превышение массы, габаритов или количества единиц продукта | `Letter`, `Parcel` |
| `IncompatibleServiceException` | Неразрешённое сочетание или недоступность услуги | `DeliveryOptions`, `ServiceRate` |
| `TariffNotFoundException` | Нет однозначно применимого тарифа на заданную дату | `WeightBand`, `TariffPlan`, `PostageCalculator` |
| `ShipmentNotFoundException` | Неизвестный трек-номер | `ShipmentRegistry`, операции поиска |
| `InvalidShipmentStateException` | Нарушение порядка истории, недопустимый переход или действие в неверном состоянии | `TrackingHistory`, `Shipment`, `DispatchBatch`, `PostalBranch`, `ReturnRequest` |
| `PaymentException` | Просроченный или чужой счёт, переплата, неверный возврат, нехватка наличности | `InvoiceLine`, `Invoice`, `Payment`, `Refund`, `CashRegister`, `CompensationClaim` |
| `StorageCapacityException` | Нет подходящего места либо превышен лимит хранения | `StorageArea`, `StorageCell`, `PostalBranch` |
| `TransportUnavailableException` | Транспорт занят, не допущен, недостаточно вместителен либо маршрут непригоден | `DispatchBatch`, `Vehicle`, `VehicleInspection`, `TransportTrip` |
| `DeliveryAuthorizationException` | Сотрудник, получатель, документ или разрешение не дают права на почтовую операцию | `IdentityDocument`, `PickupAuthorization`, операции выдачи |
| `ManifestMismatchException` | Состав, пломбы или масса рейса не совпали с ведомостью | `TransportManifest` |

Каталог содержит **14 собственных классов исключений**, включая базовый;
все они реализованы. Все тринадцать предметных исключений
проверяются unit-тестами; проверяется также перехват через базовый тип.
CLI перехватывает ошибки операций, выводит пояснение и возвращается в меню
без фиксации частичных изменений. Исключения не входят в 50 предметных
классов раздела 4.

## 6. Предметные сценарии и проверки

Все предметные подсистемы ниже доступны через библиотечный API и unit-тесты.
Ключевые процессы также доступны через отдельный интерактивный CLI;
постоянные проверки настоящего бинарника дополняют, но не заменяют unit-тесты.

| Требование или процесс | Классы и поведения | Проверки |
|---|---|---|
| Оформление письма и посылки | `Letter`, `Parcel`, `ShipmentRegistry` | Обычное оформление, лимиты, уникальность номера |
| Точная стоимость | `Money`, тарифы, `PostageCalculator` | Независимые ожидаемые суммы, границы веса и округления |
| Оплата до приёма | `PostageQuote`, `Invoice`, `CashRegister`, `PostalBranch` | Просрочка, изменённое отправление, неполная оплата |
| Хранение | `StorageArea`, `StorageCell`, `StorageEntry`, `StoragePolicy` | Лимиты места, масса, бесплатные дни, просрочка |
| Сортировка и отправка | `SortingPlan`, `MailBag`, `DispatchBatch` | Однозначное направление, пломба, отсутствие потери отправлений |
| Перевозка | `PostalRoute`, `Vehicle`, `TransportTrip`, `TransportManifest` | Порядок остановок, допуск, вместимость, подмена состава |
| Вручение | `PostalBranch`, `DeliveryTask`, `IdentityDocument`, `PickupAuthorization` | Получатель, представитель, сроки, повторная выдача |
| Неудачная доставка | `DeliveryAttempt`, `StoragePolicy`, `DeliveryRoute` | Причина отказа, лимит, интервал, перенос задания |
| Возврат | `ReturnRequest`, `Shipment`, отделения и перевозка | Основание, разрешённое состояние, обратный адрес |
| Розыск и компенсация | `SearchRequest`, `CompensationClaim`, `CashRegister` | Обязательные проверки, предел решения, выплата один раз |
| Согласованность состояния | Реестр, история, ячейки, партии, рейсы | Отправление не исчезает и не оказывается в двух местах |
| Сохранение состояния при ошибке | Все изменяющие операции | Снимок до ошибки и сравнение всех затронутых объектов после |
| Независимость копий | Значимые объекты и снимки данных | Изменение копии не меняет оригинал |
| Собственные исключения | Раздел 5 | Каждый тип реально выбрасывается и проверяется тестом |
| CLI отдельно от модели | `app/` и библиотека предметной логики | Сквозные сценарии без прямого изменения внутренних полей |

### Консольный интерфейс

В CLI доступны следующие сценарии:

1. Подготовить клиентов и оформить письмо или посылку.
2. Рассчитать стоимость и показать её состав.
3. Провести оплату и приём в отделение.
4. Отсортировать, сформировать партию и выполнить перевозку.
5. Показать историю по трек-номеру.
6. Выдать отправление либо выполнить курьерскую доставку.
7. Показать неудачную попытку, хранение и возврат.
8. Продемонстрировать розыск, решение о компенсации и выплату.

`app/Console` проверяет формат построчного ввода; `app/Application` хранит сеанс
и переводит команды в вызовы модели. Меню не меняет статусы и складские записи
напрямую. Составная команда выполняется на копии всего состояния и фиксируется
небросающим обменом только после успеха. EOF отменяет незавершённую команду.
Начальная конфигурация учебная; хранения между запусками нет.
Разделы меню, порядок работы и три проверяемых `.input`-примера описаны в [CLI.md](CLI.md).
