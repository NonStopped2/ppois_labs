# CI и выпуск lab2

Workflow: [`.github/workflows/lab2.yml`](../.github/workflows/lab2.yml).
YAML описывает действия GitHub Actions; приложение не читает этот файл.
Проверки и публикация lab1 этим workflow не выполняются.

## Когда запускается

- `push` в `feature/lab2` или `main` запускает проверки.
- `pull_request` в `main` проверяет состояние PR. Используется обычный безопасный
  `pull_request`, не привилегированный `pull_request_target`.
- `workflow_dispatch` позволяет вручную запустить проверки через Actions.
- `push` тега, начинающегося на `lab2-v`, дополнительно допускает релизную задачу.
  Публикация принимает только формат **`lab2-vX.Y.Z`** из чисел.
- Ни push ветки, ни PR, ни ручной запуск **не публикуют релиз**.
  Ни одна задача не выполняет merge, не создаёт и не переставляет тег.

Фильтров по изменённым путям нет: например, изменение корневого CMake тоже
может повлиять на lab2 и должно проходить проверки.
Для ручного `workflow_dispatch` GitHub требует наличие workflow в ветке по
умолчанию (`main`). Пока он находится только в feature-ветке, кнопка ручного
запуска может быть недоступна; первый запуск проверяется обычным push ветки.

## Устройство YAML

| Ключ | Значение в этом workflow |
|---|---|
| `name` | Название во вкладке Actions |
| `on` | События и фильтры веток/тегов, перечисленные выше |
| `permissions` | По умолчанию токен может только читать содержимое репозитория |
| `jobs` | Три задачи: `build`, `quality`, `release` |
| `runs-on` | Чистая машина GitHub для каждой задачи |
| `strategy.matrix.os` | Две независимые копии `build`: Ubuntu 24.04 x86_64 и macOS 15 arm64 |
| `fail-fast: false` | Ошибка Linux не отменяет полезные диагностические результаты macOS и наоборот |
| `env` | Переменные среды для команд; например, опции санитайзеров |
| `steps` | Последовательные действия в пределах одной задачи |
| `uses` | Готовое действие GitHub, зафиксированное полным SHA коммита |
| `with` | Параметры готового действия |
| `run` | Команды оболочки на выбранной машине |
| `needs` | Зависимость релиза от успешного `build` на обеих ОС и `quality` |
| `if` | Дополнительное условие: релиз только при push релизного тега |
| `timeout-minutes` | Ограничение времени отдельной задачи |

Важны пробельные отступы: например, `permissions` внутри `release` относится
только к публикации. Табуляция не используется. `|` перед блоком `run` сохраняет
переносы строк между командами; `>-` соединяет длинную команду в одну строку.
`${{ matrix.os }}` вычисляет GitHub при подготовке задачи, а `$RELEASE_TAG`
раскрывает оболочка уже внутри runner. Значение тега передаётся через `env`,
а не вставляется в текст исполняемой команды.

### Задача `build`

Для каждой ОС последовательно:

1. `checkout` получает исходники проверяемого коммита. `persist-credentials: false`
   не оставляет токен в настройках локального Git.
2. `setup-python` выбирает Python 3.12 для вспомогательных тестов.
3. CMake создаёт Debug-сборку с ASan/UBSan. Собираются только `post_core_tests`,
   `post_ui_tests`, `post_cli`; приложения lab1 не запускаются.
4. CTest выбирает точные метки `lab2`, `lab2-ui`, `lab2-cli`, `lab2-tools`.
   UBSan настроен на немедленную ошибку, а не только печать предупреждения.
5. Отдельный каталог Release конфигурируется с `BUILD_TESTING=OFF`,
   `BUILD_SHARED_LIBS=OFF`, без санитайзеров и профилирования.
6. `package.py` устанавливает **компонент `lab2`**, переносит каталог,
   проверяет приложение, создаёт архив и SHA-256, распаковывает его в новое
   место и снова выполняет все 13 внешних CLI-тестов с установленными примерами.
7. `upload-artifact` прикрепляет архив и `.sha256` к текущему запуску Actions.
   Отсутствие файлов считается ошибкой.

Каталоги build у разных задач не общие. Для передачи готовых пакетов между
runner используются Artifacts, а не локальные пути от предыдущей задачи.

### Задача `quality`

Работает параллельно с обеими сборками, на Ubuntu:

1. Устанавливает Clang/LLVM 18, cppcheck, Doxygen и **clang-format 18.1.8**.
2. `quality.py` проверяет все C++-файлы lab2, синтаксис Python, производственный
   код cppcheck и независимую компиляцию каждого из 99 заголовков.
3. Создаёт отдельную инструментированную LLVM-сборку.
4. Дважды запускает покрытие, каждый раз с новыми профилями:
   - только предметные C++ unit-тесты и `src/` + исполняемые строки `include/`;
   - предметные и UI C++ unit-тесты, вся область, включая `app/main.cpp`.
5. Каждая метрика должна быть **строго >90% строк**. Например, ровно 90%
   возвращает из `coverage.py` код `1`: шаг красный и релиз не разрешается.
6. Генерирует `lab2_docs`, архивирует HTML-документацию и проверяет её архив.
7. Прикрепляет JSON покрытия и пакет документации к запуску.
   `if: always()` относится только к попытке сохранить диагностику покрытия:
   оно не превращает провалившуюся проверку в успешную и не разрешает релиз.

Ошибки скриптов и тестов возвращают ненулевой код. Обычный шаг `run` завершается
ошибкой, оставшиеся обычные шаги этой задачи пропускаются. Другая независимая
задача при этом может продолжить работу. Artifacts одного успешного runner
не доказывают успешность всего workflow.

### Задача `release`

Сначала ждёт `needs: [build, quality]`. Если любая требуемая задача неуспешна,
публикация пропускается. Дополнительно проверяются событие `push` и префикс тега.

Только эта задача получает `contents: write`. Она:

1. Скачивает `lab2-release-*` из **этого же запуска**, не из старого успешного CI.
2. Проверяет полный формат тега, наличие Linux x86_64, macOS arm64 и HTML-пакета,
   затем SHA-256 каждого архива.
3. Вызывает `gh release create --verify-tag --prerelease --latest=false`.

Результат — **Pre-release**, не стабильный Latest. `--verify-tag` не позволяет
создать отсутствующий удалённый тег автоматически. Повторный запуск не
перезаписывает существующий релиз: команда `create` завершится ошибкой.

Actions зафиксированы полными SHA: checkout v4, setup-python v5,
upload-artifact v4, download-artifact v4. Обновление их версий — отдельная
проверяемая правка, а не незаметное изменение плавающего major-тега.

## Что скачивает пользователь

В Releases будут три архива, у каждого соседний `.sha256`:

- `ppois-lab2-linux-x86_64.tar.gz`;
- `ppois-lab2-macos-arm64.tar.gz`;
- `ppois-lab2-docs.tar.gz`.

Пакет приложения содержит только `bin/post_cli`, `RUNNING.txt`, четыре руководства
в `share/ppois_lab2/` и три `.input` в `share/ppois_lab2/examples/`.
Никаких build-каталогов, Catch2, тестовых бинарников или служебного контекста.
Для запуска нужны соответствующие ОС/архитектура и системная C++-библиотека,
не IDE/CMake/Python. Linux-пакет собирается на Ubuntu 24.04 и не обещает
совместимости со всеми старыми дистрибутивами. macOS deployment target — 14.0;
пакет не подписан Developer ID и не нотарифицирован Apple.

## Повторение локально

Из корня репозитория, при установленных инструментах:

```bash
python3 lab2/tools/quality.py
cmake -S . -B build/lab2-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DBUILD_SHARED_LIBS=OFF
cmake --build build/lab2-release --target post_cli --parallel 4
python3 lab2/tools/package.py --build-dir build/lab2-release --output-dir build/lab2-packages
cmake --build build --target lab2_docs
python3 lab2/tools/package.py --build-dir build --output-dir build/lab2-packages --docs-only
```

Для проверки YAML локально можно использовать `actionlint .github/workflows/lab2.yml`.
Генерация `lab2_docs` требует установленного Doxygen **на момент конфигурации CMake**;
если он установлен позже, повторите `cmake -S . -B build`. Обычная сборка приложения
Doxygen не требует. Пути инструментов качества можно задать через
`--clang-format`, `--cppcheck`, `--cxx` или `CLANG_FORMAT`, `CPPCHECK`, `CXX`.

После скачивания архива и его `.sha256` **именно из Releases**, не из Actions:

```bash
python3 lab2/tools/package.py --verify-archive /path/to/ppois-lab2-macos-arm64.tar.gz
python3 lab2/tools/package.py --verify-archive /path/to/ppois-lab2-docs.tar.gz --docs-only
```

Проверка пакета требует Python и исходного репозитория с тестовым скриптом,
обычный запуск `bin/post_cli` — нет. Проверяется нативный пакет текущей платформы.
SHA-256 подтверждает совпадение с приложенным файлом, не независимую подпись автора.
Локально проверенный архив или успешный Actions не заменяют отдельную проверку
пакета, скачанного из Releases.
