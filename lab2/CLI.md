# Консольное приложение «Почта»

## Сборка и запуск

Из корня репозитория:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target post_cli post_core_tests post_ui_tests --parallel 4
./build/lab2/post_cli --help
./build/lab2/post_cli
./build/lab2/post_cli --demo
```

Если выбран другой каталог `-B`, бинарник находится в `<build-dir>/lab2/post_cli`.
Для сборки только приложения, без Catch2 и Python для тестов, добавьте при
конфигурировании `-DBUILD_TESTING=OFF` и собирайте цель `post_cli`.
Приложение — C++20, без сторонних runtime-библиотек интерфейса.

Без `--demo` справочник клиентов и реестр отправлений пусты. Отделения, тарифы,
сотрудники, начальные смены и кассы уже заданы учебной конфигурацией.
`--demo` добавляет клиентов и два **неоплаченных черновика**, а не завершает
процессы автоматически. То же действие доступно в меню «1 → 3».
Повторная загрузка с конфликтующими ID отклоняется, пользовательские данные
не удаляются.

## Ввод и состояние сеанса

- Одна строка — один ответ. Раздел `0` завершает программу, действие `0` возвращает
  из подменю. После каждой команды снова показывается основное меню.
- Числа разбираются целиком: `12abc`, переполнение, отрицательное число вне диапазона
  и дробь вместо целого не принимаются. Поле запрашивается повторно.
- Деньги вводятся **целым числом копеек BYN**: `300` означает `3.00 BYN`.
- Даты документов — `ГГГГ-ММ-ДД`; проверяется и формат, и календарь.
- Пустая строка обозначает отсутствие квартиры, email или разрешения представителю.
  Для обязательного поля она не создаёт фиктивное значение.
- Трек-номера, отделения и ссылки на доказательства в списках разделяются запятыми:
  `BY-1,BY-2`, `A,B`. Пустые элементы и повторы отвергаются.
- Начальные учебные часы: **2026-01-01 00:00:00 UTC**. Реального ожидания нет:
  «9 → 2» переводит часы вперёд на введённое число секунд. Назад часы не переводятся.
- Окно курьера задаётся двумя смещениями в секундах от текущего времени.
  Длительность разрешения представителю тоже отсчитывается от текущего времени.
- Ошибка предметной операции возвращает в меню. Команда выполняется на копии
  **всего состояния приложения**, включая реестр, планы, кассы и счётчик служебных ID.
  При ошибке или EOF незавершённая команда не оставляет частичных изменений.
- EOF (например, Ctrl-D на пустой строке) штатно заканчивает сеанс, код возврата `0`.
  Неисправность ввода даёт `1`, неизвестные аргументы командной строки — `2`.

Все данные существуют **только до завершения процесса**. Сохранения в файлы и
базы данных нет; входные `.input` ниже — воспроизведение команд, не снимки состояния.
Отдельные успешные команды сохраняются в сеансе, отклонение последующей не отменяет их.

## Начальная учебная конфигурация

Параметры находятся в `app/Defaults.hpp` и `app/Defaults.cpp`, не в тестовых Fixtures.
Это **не официальные тарифы и правила Белпочты**.

| Настройка | Значение |
|---|---|
| Отделения | `A` обслуживает `22xxxx`, `B` — `23xxxx`, `C` — `24xxxx` |
| Сотрудники каждого отделения | `manager-A` / `courier-A` и аналогично для B/C |
| Смены | Первые 24 часа; ID `shift-manager-A`, `shift-courier-A` и аналогичные |
| Машина | `van-1`, 100000 г, 20 мешков |
| Курьер | Один на отделение, лимит 30000 г |
| Приём | До 30000 г, сторона до 1000 мм, до 1000 единиц; до 100 позиций вводимой описи |
| Склад | В каждом отделении общая и хрупкая зоны, по ячейке на 100000 г / 100 мест |
| Хранение | 7 дней, первые 2 бесплатно, затем 50 коп. за начатый день |
| Повтор доставки | До 3 попыток, минимум 1 час между ними; исходный дедлайн сохраняется |
| Дорога / обработка | 1200 с между пунктами / 300 с в пункте |
| Розыск | Минимум 3600 с до подтверждения утраты, все ожидаемые отделения проверены |
| Касса | Открыта в каждом отделении, начальная наличность 50000 коп. |
| Допуск машины | Первые 7 дней; обновляется после подтверждённого осмотра без замечаний |
| Горизонт времени | 3650 дней от начала сеанса; предложения действуют до 24 часов |

Тариф `standard`: база 300 коп., 75 коп. за дополнительный начатый шаг 1000 г.
Тариф `express`: база 600 коп., шаг 100 коп. Регистрация — 100 коп., объявленная
ценность — 1%, курьер — 250 коп., хрупкость — 100 коп., уведомление — 50 коп.
Итог и каждую строку считает `PostageCalculator`, UI не вычисляет тариф вручную.
Непокрытый индекс отвергается при расчёте.

После истечения смены операции с полномочиями запрещены. «9 → 3» закрывает
истёкшие смены выбранного отделения на их плановом конце и открывает новые.
Действующую смену таким способом заменить нельзя. Новые ID видны в «9 → 1».
«9 → 4» задаёт перерыв по ID смены; он начинает действовать немедленно.

### Данные `--demo`

| ID | Имя | Индекс |
|---|---|---|
| `sender` | Анна Отправитель | 220000 |
| `recipient` | Борис Получатель | 230000 |
| `local` | Вера Местная | 220000 |
| `rep` | Глеб Представитель | 240000 |

`BY-1` — письмо 20 г от `sender` к `recipient`, без дополнительных услуг,
стоимость `standard` **300 коп.**
`BY-2` — посылка 500 г с книгой, от `sender` к `local`, с курьерской доставкой,
стоимость `standard` **550 коп.**
Эти номера относятся к новому сеансу. При загрузке примеров позже номера
назначаются текущей последовательностью реестра и выводятся на экран.

## Основное меню

| Раздел | Действия по порядку |
|---|---|
| 1. Клиенты | 1 создать; 2 список; 3 загрузить демо |
| 2. Отправления | 1 письмо; 2 посылка; 3 список; 4 история; 5 отменить черновик; 6 изменить массу/услуги черновика |
| 3. Стоимость/оплата | 1 расчёт и новый счёт; 2 счета/журналы; 3 оплатить; 4 вернуть оплату; 5 отменить счёт без удержанных денег |
| 4. Отделение | 1 принять; 2 склад/плата за хранение; 3 выдать; 4 создать разрешение представителю; 5 отозвать |
| 5. Перевозка | 1 план мешка/партии/рейса; 2 выезд; 3 прибытие; 4 выгрузка; 5 допуск машины; 6 список |
| 6. Курьер | 1 план; 2 старт; 3 попытка; 4 финиш с возвратом; 5 новое окно прежнего задания; 6 список; 7 отмена до выезда; 8 прерывание с возвратом |
| 7. Возврат/розыск | 1 запрос возврата; 2 решение; 3 начать возврат; 4 открыть розыск; 5 проверка отделения; 6 результат розыска; 7 список обращений |
| 8. Компенсации/касса | 1 требование; 2 решение; 3 выплата; 4 касса/журналы; 5 открыть/закрыть кассу |
| 9. Время/настройки | 1 параметры/смены; 2 перевести часы; 3 новые смены; 4 перерыв |

Не требуется запоминать порядок полей: каждое поле запрашивается с подписью.
Статусы показываются именами C++ enum (`Draft`, `Accepted`, `Delivered` и т. д.).
История содержит номер события, UTC-время, вид факта, отделение и пояснение.

## Три воспроизводимые демонстрации

Из корня репозитория после сборки в `build`:

```bash
./build/lab2/post_cli --demo < lab2/examples/transport.input
./build/lab2/post_cli --demo < lab2/examples/courier.input
./build/lab2/post_cli --demo < lab2/examples/loss.input
```

Каждая команда начинает **отдельный сеанс**. Все три файла проходят постоянные
проверки настоящего бинарника.

- `transport.input`: расчёт → оплата → приём в A → план рейса → обработка 300 с →
  выезд → дорога 1200 с → прибытие B → обработка 300 с → выгрузка → документ
  получателя → `Delivered`. Машина освобождается.
- `courier.input`: местная посылка после приёма сразу `AwaitingPickup` → курьерский
  маршрут → отсутствие получателя → физический возврат → ожидание часа → повтор
  с сохранённым ID задания и журналом → вручение → финиш. Всего 2 попытки.
- `loss.input`: отрицательные физические проверки A и B → ожидание часа →
  подтверждение `Lost` с удалением учётной записи склада → требование 500 коп. →
  оценка/одобрение → однократная выплата. Возврат тарифа — отдельная операция.

Для ручного знакомства начните с `--demo`, раздела «9 → 1» и списка «2 → 3».
Затем выполните «3 → 1» для `BY-1`, ID счёта `i1`, тариф `standard`; «3 → 3»
в A, счёт `i1`, платёж `p1`, 300 коп., наличные; «4 → 1» в A для того же номера
и счёта. Дальше можно выбрать перевозку или розыск.

## Особенности согласованных процессов

- Приём и оплата — разные команды. Неполная оплата, неверное отделение, истёкший
  счёт или несоответствие версии запрещают приём без потери складского места.
- Новая версия черновика делает старое предложение непригодным для оплаты.
  Средства возвращаются через кассу; счёт отменяется проверяемой операцией,
  а не удалением из контейнера.
- План рейса создаёт один мешок и одну партию для списка номеров, но не извлекает
  груз. Рейсы CLI имеют два пункта; библиотека также поддерживает промежуточные
  остановки. Готовность партии не означает фактический выезд.
- Окно доставки строго раньше исходного дедлайна. Неудача остаётся
  `OutForDelivery` до физического возврата при финише. Повтор возможен только
  для отсутствия получателя/не найденного адреса, не для отказа/повреждения.
- Если окно истекло до выезда, «6 → 7» отменяет план и освобождает курьера,
  не изымая груз со склада. Задания получают `Cancelled`, отмена остаётся в истории.
- Если маршрут уже начат, «6 → 8» физически возвращает весь оставшийся груз,
  включая задания без попытки. Пропуск окна не записывается как отсутствие получателя.
  Нехватка места откатывает весь возврат; вручённый груз не изменяется.
- После отмены или прерывания используйте «6 → 5» с прежним маршрутом и заданием:
  его ID, журнал и исходный дедлайн сохраняются. Если были реальные неудачи,
  ограничения причины, интервала и числа попыток продолжают действовать.
  После первого выезда новое задание через «6 → 1» не заменяет исходный цикл.
- Для вручения вводится реальный для учебного сценария документ с именем и сроком.
  UI не подставляет нужное имя автоматически. Представителю необходимо действующее
  разрешение; его отзыв блокирует выдачу и курьерское вручение.
- Возврат: запрос → решение → начало → обычный обратный рейс → выдача исходному
  отправителю с `Returned`. `approve` не перемещает посылку сам по себе.
- Розыск хранит снимок истории. Новое событие требует нового актуального розыска.
  Положительная проверка и согласованный склад нужны для результата `Found`;
  отрицательные проверки могут выявить расхождение физического наличия и учёта.
- Компенсация не является возвратом оплаты. Доказательства — учебные ссылки,
  а не автоматическая экспертиза ущерба. Утрате требуется завершённый розыск.
- Карточные деньги не меняют наличность. Закрытие кассы требует точного пересчёта;
  новый сеанс кассы начинает новый журнал. Канонические объекты требований
  сохраняют состояние `Paid` и не могут быть оплачены повторно.

## Проверки

```bash
ctest --test-dir build -L '^lab2($|-)' --output-on-failure
ctest --test-dir build -L '^lab2$' --output-on-failure       # только предметные unit-тесты
ctest --test-dir build -L '^lab2-ui$' --output-on-failure    # C++ unit-тесты интерфейса
ctest --test-dir build -L '^lab2-cli$' --output-on-failure   # настоящие процессы post_cli
python3 lab2/tools/cli_tests.py ./build/lab2/post_cli
```

Python ≥3.9 нужен для вспомогательных проверок, без сторонних пакетов.
CLI-тесты не подменяют C++ unit-тесты. Покрытие измеряется отдельно:

```bash
cmake -S . -B build/lab2-coverage -DCMAKE_BUILD_TYPE=Debug -DLAB2_ENABLE_COVERAGE=ON
cmake --build build/lab2-coverage --target post_core_tests post_ui_tests post_cli --parallel 4
python3 lab2/tools/coverage.py --build-dir build/lab2-coverage
python3 lab2/tools/coverage.py --build-dir build/lab2-coverage --with-ui
```

По умолчанию: только 240 предметных C++ тестов, `src/` и исполняемые строки `include/`.
`--with-ui`: предметные и UI C++ unit-тесты, вся производственная область, включая
`app/main.cpp`. Сам `main` unit-тестами не запускается и учитывается как непокрытый,
а не молча исключается. В обоих режимах строгий порог **>90%**, новые профили и
исключение тестов, зависимостей и других лабораторных. Внешние CLI-процессы и
проверки Python в unit-профили не входят.

Workflow CI, установка и упаковка подключены: см. **[CI.md](CI.md)**.
Реальный запуск Actions и проверка скачанного из Releases пакета выполняются
после публикации; локальный запуск приложения их не заменяет.

В распакованном нативном пакете вместо `./build/lab2/post_cli` используется
`./bin/post_cli`; примеры находятся в `share/ppois_lab2/examples/`.
Состояние между запусками также не сохраняется. Для простого запуска пакета
не требуются Python, CMake или тестовые библиотеки.
