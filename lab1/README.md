# Лабораторная №1: Кубик Рубика и машина Поста

Оба варианта назначены для этой работы. Язык — C++20. Предметные классы не
читают консоль и не зависят от меню. Приложения находятся в `app/`, классы —
в `include/` и `src/`, постоянные тесты — в `tests/` каждого варианта.

## Сборка и тесты

Команды выполняются **из корня репозитория**, не из `lab1`:

```bash
cmake -S . -B build
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
```

Требования: CMake >= 3.20, компилятор C++20, Python >= 3.9 для CLI-тестов.
При первой конфигурации с тестами CMake загружает Catch2 **v3.8.1** с проверкой
SHA-256. Для сборки только приложений можно отключить эту сетевую зависимость:

```bash
cmake -S . -B build/apps -DBUILD_TESTING=OFF
cmake --build build/apps --parallel 4
```

Каждый новый build-каталог имеет собственные приложения в `lab1/`.

## Кубик Рубика

```bash
./build/lab1/rubiks_cube
./build/lab1/rubiks_cube lab1/examples/cube_solved.txt
```

Без файла игра начинается после 30 допустимых случайных поворотов. Загрузка
файла не добавляет перемешивание. В меню есть просмотр, повороты всех граней
в обоих направлениях, перемешивание, проверка сборки, сохранение, загрузка,
сброс в собранное состояние и новая случайная игра.

### Модель и формат

`RubiksCube` хранит шесть массивов по девять цветов. Координаты строки и
столбца — 0..2. Поворот по часовой стрелке определяется **при взгляде прямо
на выбранную грань**. Копирование и присваивание создают независимые состояния.

Файл содержит 54 символа, пробельные разделители произвольны. Порядок граней:
**Up, Down, Front, Back, Left, Right**. Клетки грани записываются по строкам.

| Символ | Цвет | Центр грани |
|---|---|---|
| W | Белый | Up |
| Y | Жёлтый | Down |
| G | Зелёный | Front |
| B | Синий | Back |
| O | Оранжевый | Left |
| R | Красный | Right |

Пример — `examples/cube_solved.txt`. Проверяются символы, наличие всех клеток,
девять экземпляров каждого цвета и фиксированные центры. **Полная физическая
достижимость расстановки (ориентации деталей и чётность перестановок) не проверяется.**
Случайное перемешивание применяет настоящие повороты, поэтому из собранного
кубика получает достижимое состояние, но не гарантирует, что оно несобранное.
Повторяемость seed гарантируется в рамках одной реализации стандартной библиотеки,
а не между любыми платформами. Перемешивание применяется к текущему состоянию.

## Машина Поста

```bash
./build/lab1/post_machine
./build/lab1/post_machine lab1/examples/post_mark_right.txt
./build/lab1/post_machine lab1/examples/post_increment.txt -log
./build/lab1/post_machine --help
```

Без аргументов открывается меню с примером добавления одной метки справа от
непрерывного блока. С файлом машина **сразу выполняет программу и завершает процесс**.
Успех — код 0, ошибка загрузки/выполнения/аргументов — код 1.
Файловый режим ограничен 10000 командами. В меню лимит выбирается от 1 до 1000000.
`examples/post_loop.txt` демонстрирует срабатывание ограничения, а не штатный HALT.

### Четыре класса

- `Tape`: двоичная разреженная лента и каретка. Хранятся только отмеченные координаты.
- `Instruction`: действие и переходы; конструктор отвергает неверные аргументы.
- `Program`: упорядоченное соответствие положительных номеров командам.
- `PostMachine`: собственные копии программы и ленты, текущая команда и остановка.

Лента моделирует движение в обе стороны, включая отрицательные координаты.
Практическое ограничение координат — диапазон `int64_t`; переполнение вызывает
ошибку до изменения состояния. Изменяется рабочая лента машины, а не переданный
в конструктор исходный объект. Освобождением памяти управляют стандартные контейнеры.

### Команды

| Запись | Действие и переход |
|---|---|
| `MARK n` | Поставить метку в пустую клетку, перейти к n |
| `ERASE n` | Стереть существующую метку, перейти к n |
| `LEFT n` | Сдвинуть каретку влево, перейти к n |
| `RIGHT n` | Сдвинуть каретку вправо, перейти к n |
| `IF n m` | Пусто → n, есть метка → m; лента и каретка не меняются |
| `HALT` | Остановиться без перехода |

Обычной команде нужен один положительный переход, `IF` — два. Внутри `Instruction`
неиспользуемые переходы равны 0. Номера команд могут иметь пропуски; начальная
команда — команда с **наименьшим номером**, если не восстановлено другое `CURRENT`.
Удаление команды не меняет номера остальных. Во время редактирования разрешены
ещё не существующие переходы; перед действием проверяется **выбранный** переход.

Повторная постановка метки, стирание пустой клетки, выполнение пустой программы,
отсутствующий выбранный переход и переполнение координаты — ошибки. Неуспешный
шаг не изменяет состояние. Лимит шагов сохраняет уже достигнутое состояние;
это не штатная остановка. `HALT` считается выполненной командой. Повторный `step()`
после остановки возвращает false, а `run()` — 0.

### Файл полного состояния

```text
HEAD 0
MARKS 0
PROGRAM 3
1 MARK 2
2 RIGHT 3
3 HALT
CURRENT 1
HALTED 0
```

- `HEAD`: координата каретки.
- `MARKS`: число меток, затем столько же уникальных координат.
- `PROGRAM`: число команд, затем столько же записей `номер команда`.
- `CURRENT`: следующая команда; 0 допустим только для пустой программы.
- `HALTED`: 0 или 1; 1 допустимо только при CURRENT, указывающем на HALT.

Все слова регистрозависимы. Пробелы и переводы строк служат разделителями;
комментарии форматом не предусмотрены. Дубликаты координат/номеров отвергаются.
Сохранение после шага позволяет затем продолжить выполнение, а не начать заново.
HALTED 0 на команде HALT допустим: остановку ещё предстоит выполнить.
Пустая программа допустима для редактирования, но не для исполнения.

Меню позволяет просматривать и редактировать команды, клетки и положение каретки,
выполнять шаг/программу, загружать и сохранять файлы. После ручной правки исполнение
сбрасывается на первую команду; полученная конфигурация становится исходной для
перезапуска. После загрузки можно продолжить сохранённое исполнение; перезапуск
восстанавливает загруженную ленту и начинает программу с первой команды.

При `-log` после **каждой успешной команды, включая HALT**, записываются `EXECUTED`,
лента, `CURRENT` и `HALTED`. Программа в журнале не повторяется, поскольку неизменна.
Ошибочная команда не журналируется. При ошибке записи журнала уже выполненная
команда не откатывается.

### Ошибки ввода и файлы

Оба меню проверяют целую строку числового ввода, обрабатывают EOF как выход,
поддерживают пути с пробелами и подтверждают перезапись существующего обычного файла.
CLI отвергает лишние данные после объекта в файле. Потоковые операторы читают только
свой объект и допускают цепочки. Некорректный ввод не заменяет исходный объект;
позиция чтения в потоке при этом не откатывается. Ошибки выделения памяти не являются
ошибками формата; полная транзакционная гарантия при исчерпании памяти не обещается.

## Покрытие

Нужны Clang/AppleClang и соответствующие `llvm-cov`, `llvm-profdata`:

```bash
cmake -S . -B build/coverage -DENABLE_COVERAGE=ON -DCMAKE_CXX_COMPILER=clang++
cmake --build build/coverage --parallel 4
python3 tools/coverage.py --build-dir build/coverage
python3 tools/coverage.py --build-dir build/coverage --unit-only
```

Скрипт запускает CTest с новым набором профилей, формирует JSON и HTML в
`build/coverage/coverage/`. Порог **строго >90% покрытых строк** проверяется
отдельно для каждого варианта и суммарно. Учитываются весь производственный код
в `src/`, `app/` и исполняемые строки `include/`. Тесты, Catch2, стандартная библиотека
и сгенерированные файлы не входят в знаменатель. Таким образом, учитываются и меню,
а не только классы. Режим `--unit-only` дополнительно проверяет покрытие
только классов (`src/` и исполняемые строки `include/`) исключительно Catch2-тестами,
без CLI-сценариев, с тем же строгим порогом отдельно по вариантам. Его отчёт находится
в `build/coverage/unit-coverage/`. Оба режима проверяются в CI.
Можно указать пути через `LLVM_COV` и `LLVM_PROFDATA`.

## Документация и качество

```bash
cmake -S . -B build
cmake --build build --target docs
python3 tools/quality.py
```

Doxygen создаёт HTML в `build/docs/html/index.html`; предупреждения документации
считаются ошибками. `quality.py` требует clang-format **18.1.8** и cppcheck.
Для воспроизводимого форматирования можно использовать отдельное окружение:

```bash
python3 -m venv build/tools
build/tools/bin/pip install clang-format==18.1.8
CLANG_FORMAT=build/tools/bin/clang-format python3 tools/quality.py
```

Основные unit-тесты проверяют также геометрическую модель поворотов кубика и
независимый интерпретатор 1000 программ машины Поста. CLI проверяется subprocess-сценариями.
Эти проверки не заменяют понимание кода на защите.

## CI/CD и публикация

GitHub Actions собирает и тестирует проект на Linux/macOS, проверяет форматирование,
статический анализ, покрытие и генерацию Doxygen. Пакеты приложений сохраняются как
Actions artifacts. После merge в `main` push запускает проверки и, при успехе,
публикует полноценный Release с новым тегом `lab1-main-<полный SHA проверенного коммита>`.
Публикуются Linux/macOS-пакеты и документация из того же запуска; тег привязывается
именно к собранному коммиту, даже если `main` уже продвинулся дальше.
Ручной выпуск по тегу `lab1-vX.Y.Z` также сохранён. Старые теги не переставляются,
существующие релизы не перезаписываются; повторная публикация того же тега даёт ошибку.
Прямой push в `main` тоже вызывает выпуск: одобрение PR обеспечивается процессом
и настройками GitHub, workflow сам не выполняет merge.
`--latest=false` не делает новый выпуск предварительным, а лишь сохраняет общую
метку Latest репозитория с несколькими лабораторными.
Имя архива содержит фактические ОС и
архитектуру; запуск требует соответствующей ОС, но не IDE или CMake. Linux-сборка
рассчитана на Ubuntu 24.04 или совместимую систему с нужными glibc/libstdc++.
Для macOS целевая минимальная версия — 14.0. Windows-артефакт не выпускается.

Настройка workflow в репозитории не является доказательством успешного удалённого
запуска: после разрешённого push необходимо проверить вкладку Actions и скачать
пакет. Отправка ручного тега публикует релиз, поэтому требует отдельного согласования.
Перед анализом в CI выполняется `python3 tools/test_release_workflow.py`:
проверяются условия выпуска, выбор тега и аргументы команды публикации с подставным
`gh`, без создания настоящих тегов и релизов. Локальный успех не заменяет проверку
автоматической публикации после первого одобренного merge.
